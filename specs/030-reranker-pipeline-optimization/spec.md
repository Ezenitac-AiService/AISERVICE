# Feature Specification: Reranker Pipeline & Latency Optimization (리랭커 파이프라인 및 LangGraph / Redis / 16K 대형 컨텍스트 기반 다중 타겟 RAG 오케스트레이션)

**Feature Branch**: `030-reranker-pipeline-optimization`

**Created**: 2026-08-25

**Status**: Draft

**Input**: User description: "두 챗봇(Chatbot A, Chatbot B)의 RAG 파이프라인 및 리랭커 응답 지연 분석 결과를 바탕으로, 리랭커 호출 타임아웃/후보군 파라미터 최적화, 비정상 지연 및 사일런트 폴백 방지, 두 챗봇 파이프라인 정합성 및 고속 응답 보장. 나아가 LangGraph StateGraph 상태 머신 및 Redis 4단계 다계층 캐시(L1 검색풀, L2 임베딩, L3 리랭킹, L4 체크포인터)를 도입하여 2개 이상의 제품 비교(각 제품별 병렬 분할 검색 및 리랭킹), 기능 기반 개방형 다자 비교(최대 3개 제품 자동 선정 후 병렬 검색), 단일 제품의 다중 속성/장단점 분석(긍정/부정 및 속성별 분할 검색)을 수용하는 고도화된 RAG 오케스트레이션. 특히 Qwen 3.5 2B 단일 상주 및 16K(16,384) 대형 컨텍스트 인프라를 활용하여 입력 컨텍스트 6,000토큰(타겟당 2,000토큰) 및 최대 생성 4,096토큰으로 확장 설정하고, 단일 통합 배치 리랭킹, 타겟별 쿼터 파티셔닝(비교 균형 100% 보장), 엔티티 검증 게이트, 대화 맥락 대명사 해소기, 브랜드 별칭 사전, 리뷰 XML 이스케이핑 보안, Redis 0.2초 Fail-Fast, 제품 스펙 메타데이터 번들링, 서브노드 장애 격리, SSE 연결단절 즉시 취소, TTFT 배치 튜닝, 비동기 MySQL 커넥션 풀, GPU 동시성 세마포어, Trace ID 분산 추적, 무중단 핫스왑 피처 플래그, Streamlit 동기 어댑터 및 사용자 친화적 UI 상태 출력 명세 수립"

## Clarifications

### Session 2026-08-25

- Q: 1차 검색 후 2차 리랭커(Cross-Encoder)로 전달할 최대 후보 리뷰 수(`top_k`)와 리랭커 호출 제한 시간(타임아웃)을 어떤 기준으로 표준화할까요? → A: 다중 대상을 수용하는 RAG 시스템으로, 각 분석 대상(브랜드/상품/속성)당 후보 문서 10개, 리랭커 단일 표준 타임아웃 5.0초를 적용한다.
- Q: 리랭커 타임아웃(5.0초 초과) 또는 장애로 인해 1차 코사인 유사도 폴백이 발동되었을 때, 챗봇 사용자 인터페이스(UI)에 상태를 어떤 방식으로 노출할까요? → A: 답변은 중단 없이 정상 스트리밍하되, 상단 진행 상태창 및 완료 메타데이터에 "⚡ 신속 분석 모드 (실시간 기본 검색)"로 명확히 표시하여 투명성과 친화적 UX를 보장한다.
- Q: '특정 기능에 좋은 제품들을 비교해줘'와 같이 비교 대상 제품이 특정되지 않은 개방형 질의(타입 2)가 입력되었을 때, 비교 대상 선정 정책을 어떻게 정의할까요? → A: 시스템이 해당 기능/속성 만족도 상위 대표 제품 최대 3개를 자동 선정하여 즉시 각 제품별 서브 검색 및 비교 답변을 제공하고, 추가 질의 안내를 덧붙인다.
- Q: 다중 타겟(제품/속성별) 분할 검색 및 리랭킹의 실시간 진행 과정을 챗봇 대화창에 어떤 형태의 세분화된 UI로 출력할까요? → A: 상위 4단계 파이프라인 하위에 타겟별 실시간 세부 진행 상태(예: `[1/2] 제품 A 검색 중...`, `[2/2] 제품 B 검색 완료(10건)`)가 즉각 갱신되는 계층형 실시간 서브스텝(Hierarchical Step Timeline)을 적용하여 체감 대기 시간을 줄이고 진행 가시성을 극대화한다.
- Q: LangGraph(`langgraph`, `langchain-core`)를 `oliview_core`의 공식 쿼리 오케스트레이션 엔진으로 채택하여 3대 RAG 패턴의 상태 머신(StateGraph) 및 병렬 검색 파이프라인을 구축할까요? → A: LangGraph StateGraph를 도입하여 기존 가드레일/DB/모델 자산을 100% 보존하면서 3대 질의 패턴의 조건부 라우팅, 다중 타겟 병렬 검색(Map-Reduce), 실시간 계층형 이벤트 스트리밍(`astream_events`)을 선언적 상태 그래프로 구축한다.
- Q: Redis 다계층 캐시(L1 검색풀, L2 임베딩, L3 리랭킹) 및 LangGraph Redis 체크포인터를 Chatbot A와 Chatbot B 공통 표준으로 완전히 연동하여 통합할까요? → A: Redis 4단계 다계층 캐시(L1 검색 풀, L2 질문 임베딩, L3 리랭킹 점수, L4 LangGraph 상태 체크포인터)를 전면 통합하여 Chatbot B의 캐시 우회 결함을 해소하고, 반복 질의 및 인기 상품 비교 시 0.1초대 초고속 응답을 보장한다.
- Q: 비판론자 심층 분석에서 도출된 1차 엔지니어링 보완 조치(단일 통합 배치 리랭킹, 엔티티 검증 게이트, Streamlit 동기 어댑터 등)를 어떻게 반영할까요? → A: 1차 보완 조치를 전면 수용하여 GPU 큐 병목, 프론트엔드 충돌, 오분류 왜곡을 방지하도록 스펙을 고도화한다.
- Q: Qwen 3.5 2B의 16K(16,384) 대형 컨텍스트 윈도우 인프라를 고려하여, RAG 입력 컨텍스트 예산과 LLM 최대 생성 토큰(`max_tokens`)을 어떤 수준으로 확장 설정할까요? → A: Qwen 3.5 2B 단일 상주 및 16K 컨텍스트 지원 인프라에 맞춰, 입력 컨텍스트 예산을 최대 6,000토큰(타겟당 2,000토큰)으로 대폭 확장하고, 최대 생성 토큰을 2,048~4,096토큰으로 여유롭게 설정하여 풍부한 리뷰 원문 보존과 완결형 다중 비교 리포트 생성을 보장한다.
- Q: 2차 비판론자 심층 분석에서 도출된 5대 심층 보완 조치(타겟별 쿼터 파티셔닝, TTFT 배치 튜닝, 서브노드 장애 격리, SSE 연결단절 즉시 취소, Redis 커넥션 풀)를 어떻게 반영할까요? → A: 5대 심층 보완 조치를 전면 수용하여 리랭킹 점수 쏠림 방지(타겟별 쿼터 추출), TTFT 가속(`--n_batch 2048`), 부분 장애 격리(Fault-Isolation), SSE 연결 끊김 시 GPU 연산 즉각 취소(Cancellation), Redis ConnectionPool 싱글톤을 완벽히 규정한다.
- Q: 3차 비판론자 심층 분석에서 도출된 최종 5대 무결점 조치(대화 대명사 해소기, 브랜드 별칭 사전, 리뷰 XML 이스케이핑, Redis 0.2s Fail-Fast, 제품 스펙 메타데이터 번들링)를 어떻게 반영할까요? → A: 5대 무결점 조치를 전면 수용하여 멀티턴 대명사 해소, 영문/별칭 매칭, 간접 프롬프트 인젝션 방어, Redis 0.2초 Fail-Fast, 제품 정가/용량/성분 스펙 헤더 번들링을 완벽히 규정한다.
- Q: 4차 비판론자 심층 분석에서 도출된 5대 운영/인프라 안전장치(비동기 MySQL 커넥션 풀, GPU 세마포어, Trace ID 분산 추적, 경량 의존성 핀, 핫스왑 피처 플래그)를 어떻게 반영할까요? → A: 5대 운영 안전장치를 전면 수용하여 DB 커넥션 누수 방지(`aiomysql` 풀), GPU 동시성 제어(`Semaphore 3`), Trace ID 엔드투엔드 분산 추적, 경량 코어 핀 패키지, `FEATURE_LANGGRAPH_RAG` 핫스왑 롤백 플래그를 완벽히 규정한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 명시적 다중 제품/브랜드 비교 분석 (Priority: P1)

사용자가 "CNP 프로폴리스 앰플과 식물나라 시카 토너 비교해줘"와 같이 영문 약칭이나 다중 제품 비교를 질문했을 때, LangGraph 오케스트레이터가 별칭 사전을 통해 브랜드를 정규화하고 엔티티를 검증한 후 각 제품별로 1차 검색(각 10건)을 비동기 DB 풀에서 병렬 실행하며, 통합 리랭킹 및 타겟별 쿼터 파티셔닝을 거쳐 제품 기본 스펙(가격/용량/성분)과 공정하게 선별된 리뷰(각 제품당 상위 3건)를 16K 컨텍스트에 주입함으로써 완결형 맞춤 비교 답변을 5.0초 이내에 제공받는다.

**Why this priority**: 특정 제품의 키워드 점수가 높아 한쪽 제품 리뷰로 컨텍스트가 독점되는 현상을 원천 차단하고, 영문 약칭 및 가성비/용량 스펙까지 종합 고려된 실질적 1:1 비교 답변을 보장하기 위함이다.

**Independent Test**: "CNP 프로폴리스 앰플과 식물나라 시카 토너 수분감 비교해줘" 질의 시, CNP가 차앤박으로 자동 정규화되고 두 제품의 스펙 헤더(정가, 용량)와 리뷰가 각각 3건씩 고르게 선별되어 4,096토큰 이내의 완결형 비교 표가 생성되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 2개 제품 비교 질문이 입력되었을 때, **When** LangGraph 오케스트레이터가 동작하면, **Then** 각 제품별로 독립된 하이브리드 검색(제품당 10건)을 병렬 수행하고, 수집된 전체 후보군을 1회 통합 배치로 리랭킹한 뒤 각 제품별 상위 3건씩 독립 쿼터로 선별하여 두 제품의 비교 근거를 100% 동등하게 수집한다.
2. **Given** 리랭킹이 완료되었을 때, **When** LLM 답변이 생성되면, **Then** A 제품과 B 제품의 정가/용량 대비 가성비, 속성별 장단점 비교 및 종합 추천 결론이 각 제품의 실제 사용자 리뷰에 기반하여 도출된다.

### User Story 2 - 멀티턴 대화 맥락 대명사 해소 비교 (Priority: P2)

사용자가 이전 대화 턴에서 특정 제품을 상담한 후, 후속 질문으로 "그거랑 식물나라 토너 비교해줘"와 같이 대명사("그거")를 사용했을 때, 시스템이 Redis L4 대화 히스토리에서 직전 제품("차앤박 앰플")을 자동으로 복원하여 누락 없는 정상 비교 답변을 제공받는다.

**Why this priority**: 멀티턴 챗봇 환경에서 사용자가 매번 긴 제품명을 반복 입력하지 않고 자연스러운 대화 흐름 속에서 연속 비교를 진행할 수 있도록 하기 위함이다.

**Independent Test**: 1턴에서 "차앤박 프로폴리스 앰플 어때?" 질의 후, 2턴에서 "그거랑 식물나라 토너 비교해줘" 질의 시, '그거'를 '차앤박 프로폴리스 앰플'로 해소하여 차앤박 vs 식물나라 비교 파이프라인이 정상 구동되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 이전 턴에 특정 제품이 언급된 상태에서, **When** 사용자가 "그거랑 [제품B] 비교해줘"를 입력하면, **Then** 시스템은 직전 턴의 제품을 타겟 A로 복원하여 정상 2개 타겟 비교 검색을 수행한다.

### User Story 3 - 특정 기능/효과 중심의 개방형 다자 비교 추천 (Priority: P3)

사용자가 "속건조에 좋다는 평이 많은 인기 앰플들 비교 추천해줘"와 같이 구체적 제품명을 명시하지 않고 기능/효과 기반의 비교를 요청했을 때, 시스템이 해당 기능에서 만족도가 가장 높은 대표 제품 최대 3개를 자동 선별하고, LangGraph 서브그래프를 통해 각 제품별 병렬 리뷰 검색, 통합 배치 리랭킹 및 타겟별 쿼터 추출을 거쳐 6,000토큰 입력 예산 내에서 한눈에 파악할 수 있는 다자 비교 솔루션을 제공받는다.

**Why this priority**: 사용자가 제품명을 알지 못하는 탐색 단계에서도 시스템이 자동으로 신뢰할 수 있는 상위 대표 제품군을 발굴하고 각 제품의 리뷰 근거를 독립 수집하여 고품질 비교 가이드를 제시하기 위함이다.

**Independent Test**: "진정 효과 좋은 스킨케어 제품들 비교해줘" 질의 시, 시스템이 진정 속성 상위 3개 제품을 자동 선정하고, 각 제품별 10건 병렬 검색, 통합 리랭킹 및 각 제품별 상위 2건씩 총 6건 균형 추출을 거쳐 3개 제품 비교 표/분석을 생성하는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 특정 속성/기능에 대한 개방형 비교 질의가 주어졌을 때, **When** 시스템이 분석을 시작하면, **Then** 해당 속성 긍정 만족도 기준 상위 대표 제품 최대 3개를 선별하고, 선별된 3개 제품 각각에 대해 병렬 서브 검색을 진행한다.
2. **Given** 3개 제품의 검색 및 리랭킹이 완료되었을 때, **When** 답변이 출력되면, **Then** 각 제품별 특장점과 추천 피부 타입이 명확히 비교 정리되어 출력된다.

### User Story 4 - 단일 제품의 다중 속성 및 장단점 객관 분석 (Priority: P4)

사용자가 "특정 제품의 장단점을 솔직하게 분석해줘" 또는 "수분감과 흡수력 알려줘"와 같이 다중 속성/장단점을 질문했을 때, 시스템이 긍정/장점 리뷰와 부정/주의점 리뷰, 또는 각 평가 속성별 서브 질의로 분할하여 편향 없는 객관적인 분석 결과를 제공받는다.

**Why this priority**: 긍정적인 리뷰만 편향 수집되거나 특정 속성 리뷰만 과다 추출되는 문제를 방지하고, 실사용자의 칭찬과 아쉬운 점을 모두 포괄하는 신뢰성 높은 뷰티 컨설팅을 제공하기 위함이다.

**Independent Test**: "헤라 블랙쿠션 장단점과 밀착력 지속력 알려줘" 질의 시, 긍정 피드백(장점 3건)과 부정/주의점 피드백(단점 3건)이 고르게 쿼터 선별되어 균형 잡힌 분석 답변이 도출되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 단일 제품의 장단점 또는 2개 이상의 복합 속성 질의가 주어졌을 때, **When** 검색이 수행되면, **Then** 긍정 피드백과 부정/개선점 피드백(또는 각 속성별)으로 분할 검색을 수행하여 속성당/극성당 5~10건의 후보군을 수집한다.
2. **Given** 수집된 리뷰가 리랭킹되었을 때, **When** 답변이 생성되면, **Then** 1. 장점 및 기대 효과, 2. 단점 및 주의 사항 항목이 균형 있게 구성된다.

### User Story 5 - Redis 다계층 캐시를 통한 반복 질의 초고속(0.1초대) 즉시 응답 (Priority: P5)

사용자가 동일한 화장품 질문을 반복 입력하거나 사전 프리셋 질문을 클릭했을 때, 시스템이 Redis L1(검색 풀), L2(임베딩), L3(리랭킹 점수) 캐시에서 즉시 히트(Cache Hit)하여 GPU 모델 호출 대기 없이 0.1초 이내에 답변 생성을 개시한다.

**Why this priority**: 인기 상품 질의나 반복 세션에서 불필요한 GPU 모델 게이트웨이 연산 및 DB 부하를 원천 차단하고, 사용자에게 즉각적인 체감 성능을 제공하기 위함이다.

**Independent Test**: "차앤박 프로폴리스 앰플 수분감과 흡수력 알려줘" 질의를 2회 연속 실행했을 때, 2회차 질의에서는 1단계 검색 및 2단계 리랭킹 소요 시간이 각각 1ms 미만으로 측정되며 즉시 토큰 생성이 시작되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이미 한 번 이상 처리된 화장품 질문이 재입력되었을 때, **When** RAG 파이프라인이 가동되면, **Then** Redis L2(임베딩) 및 L3(리랭킹 점수) 캐시에서 즉시 조회되어 전처리 지연 시간 10ms 이내로 답변 스트리밍이 시작된다.

### User Story 6 - LangGraph 이벤트 기반 실시간 계층형 타임라인 UI 출력 및 안전 폴백 (Priority: P6)

사용자는 다중 타겟 검색 및 리랭킹이 진행되는 동안, LangGraph의 노드 전환 및 스트리밍 이벤트를 통해 세분화된 실시간 진행 서브스텝(예: `[1/2] 차앤박 앰플 수집 중...` → `[1/2] 10건 완료`)을 즉시 확인하며 체감 대기 시간을 최소화하고, 지연 발생 시 5.0초 내 안전 폴백 및 사용자 친화적 상태 표시("⚡ 신속 분석 모드")를 제공받는다.

**Why this priority**: 다중 서브 검색으로 인해 여러 단계가 순차 진행될 때, 사용자에게 진행 상황을 세분화하여 실시간 피드백함으로써 시스템 멈춤 오해를 없애고 파이프라인 투명성을 높이기 위함이다.

**Independent Test**: 다중 비교 질문 입력 즉시 상태창에 분해된 대상 목록이 나타나고, 각 대상의 검색/리랭킹 완료 여부가 순차적으로 실시간 체크 표시되며, 5.0초 초과 시 "⚡ 신속 분석 모드 (실시간 기본 검색)"로 전환되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 2개 이상의 다중 대상 검색이 시작되었을 때, **When** LangGraph 노드에서 각 타겟별 검색이 완료될 때마다, **Then** 상태 컨테이너에 `[1/N] 대상명 검색 완료(10건)` 서브 항목이 실시간으로 추가/갱신된다.
2. **Given** 다중 대상 질의에 대해 리랭커 연산이 5.0초를 초과할 때, **When** 타임아웃이 감지되면, **Then** 시스템은 대기 없이 즉시 각 대상의 1차 유사도 순위로 폴백하여 답변 스트리밍을 시작하고 상태창에 "⚡ 신속 분석 모드 (실시간 기본 검색)"를 표시한다.

### Edge Cases

- **비교 대상이 4개 이상으로 과도한 경우**: 사용자가 4개 이상의 제품을 동시 비교 요청하더라도, 시스템은 단일 턴 질의 안정성을 위해 최대 3개 제품까지만 우선 비교하고 나머지 제품은 후속 질문으로 유도하여 5.0초 타임아웃과 16K 컨텍스트 예산을 엄격히 준수한다.
- **다중 사용자 동시 접속 폭주 (VRAM 세마포어)**: 동시 사용자가 5명 이상 몰리더라도 `asyncio.Semaphore(3)` 가드를 통해 최대 3개 요청만 GPU에서 동시 처리하고, 초과 요청은 안전하게 인메모리 큐잉하여 VRAM OOM을 원천 차단한다.
- **긴급 롤백 상황 발생 시 (피처 플래그)**: 신규 LangGraph 오케스트레이터 배포 후 예기치 못한 이슈 발생 시, 환경 변수 `FEATURE_LANGGRAPH_RAG=false` 설정으로 0초 만에 레거시 파이프라인으로 무중단 핫스왑 롤백한다.
- **다중 병렬 노드 중 1개 타겟 DB 일시 장애 (부분 장애 격리)**: 제품 A, B 병렬 검색 중 제품 B의 DB 조회가 실패하더라도 전체 그래프가 크래시되지 않고, 실패한 타겟 에러를 기록한 후 성공한 제품 A의 리뷰를 기반으로 안전하게 답변 생성을 완결한다.
- **클라이언트 탭 닫힘 / 이탈 시 GPU 리소스 보호**: 사용자가 스트리밍 도중 브라우저 탭을 닫거나 새로고침하면, FastAPI SSE 레이어에서 단절을 감지하여 즉시 LangGraph 태스크 및 GPU 토큰 생성을 취소(Abort)한다.
- **엔티티 오추출(색상 옵션, 일반 명사 오인) 발생 시**: 추출된 2차 대상이 MySQL의 등록 브랜드/상품 사전에 부합하지 않는 경우, 파이프라인 에러를 내지 않고 유효한 주 대상 중심의 단일 질의(`PATTERN_SINGLE_TARGET`)로 자동 안전 전환한다.
- **16K 대형 컨텍스트 윈도우 보호**: Qwen 3.5 2B의 16K(16,384) 윈도우 내에서, 입력 컨텍스트 예산을 **최대 6,000토큰(타겟당 2,000토큰)**으로 캡핑하고 생성 토큰을 최대 4,096토큰으로 제한하여 VRAM 초과 및 추론 속도 저하를 원천 차단한다.
- **Redis 일시 장애 시 Graceful Degradation (0.2s Fail-Fast)**: Redis 커넥션 타임아웃(0.2초) 초과 시, 블로킹 대기 없이 로컬 인메모리 및 직접 GPU 호출 모드로 즉각 무중단 폴백(Fallback)한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (LangGraph StateGraph 오케스트레이션 엔진)**: 시스템은 `langgraph` 기반의 `StateGraph`를 도입하여 RAG 파이프라인의 상태 머신, 노드 라우팅, 에러 핸들링을 선언적으로 구축해야 한다.
- **FR-002 (질의 의도 및 라우팅 분류 노드)**: `intent_router_node`는 입력 질문을 분석하여 다음 4가지 패턴 중 하나로 상태를 분기해야 한다:
  1. `PATTERN_EXPLICIT_COMPARE`: 2개 이상의 명시적 제품/브랜드 비교 질의
  2. `PATTERN_FEATURE_DISCOVERY`: 특정 기능/속성 기반의 개방형 다자 비교 추천 질의
  3. `PATTERN_ASPECT_PROS_CONS`: 단일 제품의 다중 속성 또는 장단점 심층 분석 질의
  4. `PATTERN_SINGLE_TARGET`: 일반 단일 제품/속성 질의 (기본 경로)
- **FR-003 (다중 타겟 병렬 검색 노드)**:
  - `PATTERN_EXPLICIT_COMPARE` 질의 시, LangGraph의 `Send` API를 통해 **각 제품당 10건씩** 독립 하이브리드 검색을 병렬(Parallel) 수행해야 한다.
- **FR-004 (기능 기반 대표 제품 자동 선별)**:
  - `PATTERN_FEATURE_DISCOVERY` 질의 시, 시스템은 해당 기능/속성 긍정 평가 기준 **상위 대표 제품 최대 3개**를 자동 선별하고, 선별된 각 제품당 10건의 병렬 서브 검색을 수행해야 한다.
- **FR-005 (속성/극성별 균형 검색)**:
  - `PATTERN_ASPECT_PROS_CONS` 질의 시, 시스템은 긍정(장점) 리뷰와 부정(주의점) 리뷰(또는 질문된 각 속성)를 분할 검색하여 속성/극성당 5~10건의 균형 있는 후보 문장을 수집해야 한다.
- **FR-006 (단일 통합 배치 리랭킹 및 타겟별 쿼터 파티셔닝)**:
  - `reranker_node`는 수집된 각 타겟별 후보 문장(총 10~30건)을 단 1회의 통합 배치 요청(Single Batch)으로 8091 리랭커에 전송(5.0초 표준 타임아웃)한 뒤, **타겟별 쿼터 파티셔닝(각 대상당 상위 2~3건씩 독립 선별)**을 적용하여 특정 제품으로의 점수 쏠림 현상을 원천 방지해야 한다.
- **FR-007 (안전 폴백 가드레일)**:
  - 리랭커 호출이 5.0초를 초과하거나 통신 실패 시, 로컬 CPU 딥러닝 추론을 강제하지 않고 **즉각적인 1차 유사도 순위 유지 폴백**으로 안전 전환해야 한다.
- **FR-008 (계층형 실시간 서브스텝 UI 출력)**:
  - LangGraph 노드 실행 이벤트(`astream_events`)를 수신하여, 상위 4단계 파이프라인 하위에 **타겟별 검색 및 리랭킹 진행 상태(예: `[1/N] 제품명 검색 중...` → `[1/N] 제품명 10건 수집 완료`)를 100ms 이내 실시간으로 갱신**하여 출력해야 한다.
- **FR-009 (친화적 UX 폴백 상태 노출)**:
  - 리랭커 폴백 발동 시, 답변 스트리밍은 중단 없이 정상 진행하되 상단 진행 상태창(Status Box / Timeline) 및 완료 메타데이터에 **"⚡ 신속 분석 모드 (실시간 기본 검색)"** 상태를 명시적으로 노출해야 한다.
- **FR-010 (Chatbot A/B 파이프라인 정합성)**:
  - Streamlit(Chatbot A)과 FastAPI(Chatbot B)는 동일한 LangGraph StateGraph 엔진, 타겟당 10건 후보군 정책, 계층형 서브스텝 이벤트 프로토콜, 5.0초 타임아웃 인터페이스를 공유해야 한다.
- **FR-011 (단축 경로 지원)**:
  - 1차 검색된 후보 문서 수가 대상당 3건 이하인 경우, 리랭커 호출을 자동으로 생략하고 즉시 답변 생성 단계로 연결하는 단축 경로(Short-circuit)를 지원해야 한다.
- **FR-012 (기존 보안 가드레일 100% 보존)**:
  - `oliview_core/guardrail.py`의 4단계 프롬프트 인젝션 방어 가드레일은 LangGraph 노드 내부에서 무결하게 보존 및 재사용되어야 한다.
- **FR-013 (Chatbot B의 Redis 캐시 우회 결함 해소 및 통합)**:
  - Chatbot B(`project_ragapi.py`)는 독자적인 `httpx` 직접 호출을 폐지하고 `oliview_core/client.py`의 공통 클라이언트로 일원화하여 **Redis L2(임베딩) 및 L3(리랭킹 점수) 캐시 계층을 100% 정상 활용**해야 한다.
- **FR-014 (Redis 4단계 다계층 캐시 & 커넥션 풀 싱글톤)**:
  - 시스템은 전역 `redis.ConnectionPool` 싱글톤을 기반으로 다음 4가지 캐시 계층을 운영해야 한다:
    1. `L1`: 1차 검색 결과 풀 캐시 (`v1:rag:pool:{target}:{attr}`, TTL 12h, Single-flight lock 적용)
    2. `L2`: 질문 임베딩 벡터 캐시 (`emb:bge-m3:{hash}`, TTL 7d)
    3. `L3`: 리랭커 교차 유사도 점수 캐시 (`rerank:{q_hash}:{docs_hash}`, TTL 24h)
    4. `L4`: LangGraph 멀티턴 세션 체크포인터 (`checkpoint:{session_id}`, TTL 3d)
- **FR-015 (엔티티 유효성 검증 게이트)**:
  - 시스템은 분해된 서브 타겟이 실제 데이터베이스의 등록 브랜드/상품명과 일치하는지 사전 검증하고, 유효하지 않은 보조 타겟은 단일 질의(`PATTERN_SINGLE_TARGET`)로 안전 전환해야 한다.
- **FR-016 (16K 대형 컨텍스트 및 토큰 예산 관리기)**:
  - 시스템은 Qwen 3.5 2B의 16K 윈도우 인프라를 활용하여 **입력 컨텍스트 최대 6,000토큰(타겟당 2,000토큰)**을 허용하고, **최대 생성 토큰(`max_tokens`)을 2,048~4,096토큰**으로 확장 설정하여 상세 리뷰 원문과 완결형 다중 비교 리포트를 온전히 수용해야 한다.
- **FR-017 (Streamlit 동기 제너레이터 어댑터)**:
  - Chatbot A(Streamlit)의 스레드 안전성과 렌더링 무결성을 위해, LangGraph의 비동기 스트림 이벤트를 동기 제너레이터로 래핑 변환하는 `StreamlitGraphAdapter`를 제공해야 한다.
- **FR-018 (서브노드 레벨 부분 장애 격리)**:
  - 다중 병렬 검색 시 특정 서브 타겟의 검색이 실패하더라도 전체 파이프라인을 중단하지 않고, 성공한 타겟의 리뷰만으로 답변 생성을 이어가는 `Fault-Isolation`을 보장해야 한다.
- **FR-019 (클라이언트 단절 감지 및 GPU 태스크 즉각 취소)**:
  - FastAPI SSE 스트리밍 루프 내에서 클라이언트 연결 끊김(`await request.is_disconnected()`) 감지 시, 실행 중인 LangGraph 및 GPU 토큰 생성 작업을 즉시 취소(Abort)하여 자원 누수를 차단해야 한다.
- **FR-020 (TTFT 가속을 위한 모델 게이트웨이 배치 최적화)**:
  - 모델 서빙 게이트웨이는 대형 프롬프트 처리 가속을 위해 `--n_batch 2048 --n_ubatch 512` 배치를 적용하고 고정 시스템 프롬프트의 KV 캐시 재사용을 지원해야 한다.
- **FR-021 (대화 맥락 대명사 해소기)**:
  - 시스템은 멀티턴 대화에서 "그거", "이 제품", "전자/후자"와 같은 대명사 질의 시, Redis L4 세션 히스토리에서 직전 턴에 언급된 대상 엔티티를 자동 복원하여 타겟을 구성해야 한다.
- **FR-022 (브랜드/상품 유의어 및 별칭 매핑 사전)**:
  - 시스템은 영문 약칭(`CNP`→`차앤박`, `Dr.G`→`닥터지`) 및 공백 불일치를 정규화하는 `AliasDictionary`를 검색 프리필터로 적용해야 한다.
- **FR-023 (리뷰 텍스트 간접 프롬프트 인젝션 방어)**:
  - 시스템은 XML 샌드박스 주입 전, 모든 리뷰 본문에 대해 HTML/XML 특수문자 이스케이핑(`&lt;`, `&gt;`, `&amp;`)을 강제하여 태그 탈출 공격을 원천 차단해야 한다.
- **FR-024 (Redis 0.2초 Fail-Fast 타임아웃)**:
  - Redis 클라이언트는 `socket_timeout=0.2s`, `socket_connect_timeout=0.2s`를 적용하여, Redis 지연 시 0.2초 이내에 비차단 GPU 직접 모드로 즉각 Fail-Fast 폴백해야 한다.
- **FR-025 (제품 스펙 메타데이터 헤더 번들링)**:
  - 각 타겟별 컨텍스트 조립 시, 리뷰 본문 상단에 정가, 용량, 주성분, 권장 피부타입 정보(`ProductSpecHeader`)를 1줄 번들링하여 가성비 및 객관 스펙 비교를 보장해야 한다.
- **FR-026 (비동기 MySQL 커넥션 풀)**:
  - 시스템은 병렬 검색 시 커넥션 누수를 방지하기 위해 `aiomysql.create_pool(maxsize=10)` 기반의 싱글톤 커넥션 풀을 운영하고 컨텍스트 매니저를 통해 안전하게 반납해야 한다.
- **FR-027 (GPU 동시성 제어 세마포어)**:
  - 게이트웨이 클라이언트는 동시 사용자 접속 시 VRAM 초과를 방지하기 위해 `asyncio.Semaphore(3)`를 적용하여 최대 3개의 동시 GPU 연산만 인입시키고 초과분은 안전하게 대기시켜야 한다.
- **FR-028 (엔드투엔드 Trace ID 분산 추적)**:
  - 모든 질의 요청은 고유 `trace_id`를 발급받아 LangGraph 노드, Redis 로그, SSE 이벤트에 전파되며 구조화된 JSON 실행 메트릭을 출력해야 한다.
- **FR-029 (경량 헤드리스 패키지 의존성 핀)**:
  - 오케스트레이션 엔진은 충돌 및 오버헤드를 배제하기 위해 `langgraph>=0.2.0,<0.3.0`, `langchain-core>=0.3.0,<0.4.0` 코어 패키지만을 핀 고정하여 사용해야 한다.
- **FR-030 (무중단 핫스왑 피처 플래그)**:
  - 시스템은 환경 변수 `FEATURE_LANGGRAPH_RAG=true/false`를 통해 비상 시 0초 만에 레거시 파이프라인으로 전환 가능한 핫스왑 안전망을 제공해야 한다.

### Key Entities

- **RagGraphState**: LangGraph의 전역 상태 딕셔너리 (사용자 입력, 분류된 패턴, 검증된 타겟 목록, 타겟별 검색 풀, 리랭킹 결과, 쿼터 파티셔닝 컨텍스트, 에러/폴백 플래그, 부분 장애 이력, 대화 맥락 엔티티, trace_id).
- **TraceContext**: 요청별 고유 식별자(`trace_id`), 시작 타임스탬프, 노드별 소요 시간 프로파일을 보관하는 분산 추적 엔티티.
- **GpuConcurrencyThrottle**: 동시 GPU 인입량을 3건으로 제한하는 세마포어 중재 엔티티.
- **TargetQuotaSelector**: 단일 배치 리랭킹 결과에서 타겟별로 공정하게 상위 2~3건의 리뷰를 추출하는 쿼터 파티셔닝 엔티티.
- **ProductSpecHeader**: 제품 정가, 용량, 주성분, 권장 피부타입 메타데이터 엔티티.
- **AliasDictionaryProfile**: 영문/한글 브랜드 별칭 및 공백 정규화 매핑 사전 엔티티.
- **TargetSubStepEvent**: 타겟 식별자, 타겟명, 서브스텝 코드(`TARGET_SEARCH_START`, `TARGET_SEARCH_DONE`, `TARGET_RERANK_DONE`), 수집 건수, 경과 시간을 포함하는 실시간 UI 이벤트 엔티티.
- **TargetReviewPool**: 특정 분석 대상(제품/속성/극성)에 대해 1차 검색된 10건의 후보 리뷰 컬렉션.
- **ConsolidatedBatchRerankPayload**: 다중 타겟 후보군을 1회 호출로 통합한 리랭커 배치 페이로드 엔티티.
- **TokenBudgetProfile**: 타겟당 최대 2,000토큰, 전체 6,000토큰 입력 컨텍스트 및 최대 4,096 출력 토큰 정책을 정의하는 토큰 예산 관리 엔티티.
- **RedisCacheSchema**: L1(검색 풀), L2(임베딩), L3(리랭킹 점수), L4(세션 체크포인트)의 버전 태깅 키 명명 규칙 및 TTL 정책 정의 엔티티.
- **PipelineExecutionMetrics**: 패턴 유형, 타겟 수, 단계별 지연 시간, TTFT 지연, 캐시 히트 여부(L1/L2/L3), 리랭커 폴백 여부, 총 소요 시간을 기록하는 성능 관측 엔티티.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001 (단일 질의 리랭킹 소요 시간)**: 단일 대상 질의(후보 10건)에 대한 2차 리랭킹 소요 시간이 **1.5초 이내(최대 2.0초 이내)**로 완료된다.
- **SC-002 (다중 비교 질의 병렬 검색 및 통합 리랭킹 속도)**: LangGraph 병렬 검색 및 단일 통합 배치 리랭킹 적용으로 2~3개 대상 비교 질의(후보 20~30건)에 대한 검색+리랭킹 소요 시간이 **5.0초 타임아웃 이내(평균 3.0초 내외)**로 정상 완료된다.
- **SC-003 (전체 E2E 응답 시간 개선)**: 단일 질의 기준 전체 응답 시간 **평균 4.5초 이내**, 2~3개 제품 다중 비교 질의 기준 **최대 8.0초 이내**로 완료된다.
- **SC-004 (반복/인기 질의 캐시 응답 0.1초대 달성)**: 동일 질문 또는 캐시 히트 질의 시 L1~L3 Redis 캐시를 통해 **전처리 지연 시간 10ms 이내, 전체 응답 시간 0.2초 이내**로 즉시 시작된다.
- **SC-005 (비교 질의 근거 균형성 100%)**: 쿼터 파티셔닝을 통해 다중 제품 비교 질의 시 특정 제품으로의 편향률을 0%로 만들고 **모든 비교 대상 제품의 리뷰가 각각 1건 이상 고르게 인용**된다.
- **SC-006 (실시간 서브스텝 UI 렌더링 지연 100ms 이내)**: LangGraph 노드 이벤트 발행 시 **100ms 이내에 실시간 UI 타임라인에 서브 항목이 반영**된다.
- **SC-007 (리랭커 실질 적용률 95% 이상)**: Chatbot B의 타임아웃 사일런트 폴백을 해소하고 **실제 질의의 95% 이상에서 리랭커가 정상 반영**되도록 보장한다.
- **SC-008 (A/B 챗봇 성능 정합성)**: Chatbot A와 Chatbot B 간의 전처리(검색+리랭킹) 소요 시간 격차가 **1.0초 이내**로 정합된다.
- **SC-009 (16K 컨텍스트 안정성 및 완결형 응답)**: 6,000토큰 대형 컨텍스트 주입 및 최대 4,096토큰 출력 환경에서도 **VRAM 초과율 0% 및 답변 중도 잘림 현상 0건**을 달성한다.
- **SC-010 (부분 장애 시 가용성 100%)**: 다중 타겟 병렬 검색 중 1개 타겟 DB 에러 발생 시에도 **500 서버 에러율 0%를 유지하고 잔여 타겟 기반 응답 완결율 100%를 보장**한다.

## Assumptions

- Python 3.12 런타임 환경에 `langgraph >= 0.2.0, < 0.3.0`, `langchain-core >= 0.3.0, < 0.4.0`, `redis`, `aiomysql` 라이브러리를 안전하게 설치하여 구동할 수 있다.
- Docker 인프라 내의 `vllm-serv-gateway`는 Qwen 3.5 2B(`--n_ctx 16384 --n_batch 2048`, FlashAttention 가속)를 단일 resident 모델로 8089/8081 포트에서 안정적으로 서빙하고 있다.
- Docker 인프라 내의 `aiservice-redis` (Redis 7 Alpine)는 상시 가동 중이며, L1~L4 캐시 데이터를 전역 커넥션 풀을 통해 안정적으로 인메모리 서빙할 수 있다.
- 보조 모델 서빙 게이트웨이(vllm-serv-gateway)는 BGE-M3(8090) 및 BGE-Reranker-v2-M3(8091) 인스턴스를 유지하며, 10~30건의 통합 배치 요청에 대해 5.0초 이내 응답 가능한 하드웨어 자원을 보유하고 있다.
- 분석 대상당 상위 10개의 핵심 리뷰 후보군만으로도 사용자 질문에 대응하는 충분한 도메인 정밀도와 다양성을 확보할 수 있다.
- Streamlit(Chatbot A)과 FastAPI/SSE(Chatbot B) 클라이언트는 스트리밍 세부 이벤트를 각각 `StreamlitGraphAdapter`와 `astream_events`를 통해 수신하여 동적 하위 리스트를 실시간 갱신할 수 있다.
