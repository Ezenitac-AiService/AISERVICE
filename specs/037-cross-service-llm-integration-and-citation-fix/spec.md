## 1. 개요 및 배경 (Overview & Background)

Spec 036을 통해 Model Gateway는 **Qwen 3.5 2B (64K Standard / 128K Ultra) 실시간 상시 서빙**과 **Qwen 3.5 4B (32K) 고품질 온디맨드 배치 서빙**의 2-Tier 아키텍처를 공식 완비하였습니다.

본 프로젝트는 **기술 실증(POC) 및 시연** 플랫폼으로서, "규칙 및 파이썬 알고리즘의 초고속·결정론적 특성"과 "LLM의 뛰어난 문맥 이해·추론 능력"을 파이프라인 전 단계에서 상호 보완적으로 결합하는 **'다중 하이브리드 시너지 (Multi-Strategy Hybrid Synergy)'** 및 **'LangGraph 노드 도구화 (Tool-Augmented Agentic Pipeline)'**를 표준 아키텍처로 도입합니다.

본 명세서의 4대 핵심 구현 축은 다음과 같습니다:
1. **상호보완형 다중 하이브리드 파이프라인 & LangGraph 도구화**:
   - **전처리**: Kiwi 형태소 Fast-Path(<3ms) + Qwen 2B SLM Arbiter Fallback(<60ms) + MySQL Catalog Grounding.
   - **도구화**: `search_oliveyoung_catalog`, `get_product_reviews`, `get_product_spec_header`를 LangGraph 재사용 도구로 캡슐화.
   - **후처리**: LLM 사실적 스트리밍 + Python 인용 태그 정규화 가드레일(`[1]` $\rightarrow$ `[리뷰 1]`).
2. **2단계 Top-P (문서 리랭킹 동적 Top-P + Qwen 토큰 생성 Top-P)**:
   - BGE-Reranker 점수 85% 누적 질량 가변 선별 및 점수 절벽($\Delta > 0.25$) 컷오프를 통한 하위 노이즈 완벽 배제.
   - Qwen 3.5 토큰 생성 시 `top_p=0.85`, `temperature=0.3`, `repetition_penalty=1.05` 적용.
3. **실증 데모 친화적 운영 모드(Dev vs Prod) 및 파이프라인 투명성**:
   - 개발/실증 모드에서 프리필 및 추론 타임아웃을 넉넉히(Sliding 45s, Total 180s) 설정하여 조기 타임아웃 방지.
   - 완전 눈속임이 아닌 **실제 파이프라인 단계(의도 분석 $\rightarrow$ 검색 $\rightarrow$ 리랭킹 $\rightarrow$ 스트리밍)**를 실시간 시각화.
   - 사용자 주도 **생성 중단(Stop Generation)** 기능 및 서버 장애 시 **정직하고 투명한 에러 통지**.
4. **크로스 서비스(A-Team / B-Team) LLM 호출 표준화**:
   - PILOS 감성 리포트는 4B 32K 배치로, 챗봇 대화는 2B 64K 상시 모델로 일관되게 라우팅.

## Clarifications

### Session 2026-08-26
- **Q: 특정 상품명이 없는 카테고리/속성 추천 질문(예: "민감성 피부에 좋은 쿠션팩트 추천해줘")이 입력되었을 때, 챗봇(ChatA/ChatB)의 최적 검색 및 응답 정책을 어떻게 확정할까요?** → **A: Option A 확정. 카테고리(`쿠션팩트`) 및 속성(`민감성/진정`) 키워드를 자동 매핑하여 올리브영 DB의 상위 평점 실존 상품 3~5개를 후보로 자동 발굴(Discovery)하고, 각 제품별 실제 리뷰(`[리뷰 1]`, `[리뷰 2]`)를 인용하여 비교 추천하며, DB에 매칭 제품이 전혀 없을 때만 정직한 재질의 안내를 제공하도록 확정함.**
- **Q: 복수 상품을 비교하거나 카테고리 추천 시, 답변 본문에서 각 제품별 리뷰 인용 태그([리뷰 N])의 표기 형식을 어떻게 통일할까요?** → **A: Option A 확정. 단일 제품 질문은 `[리뷰 1]`, `[리뷰 2]`, 복수 제품 비교/추천 질문은 `[제품명A 리뷰 1]`, `[제품명B 리뷰 1]` 형태의 네임스페이스 인라인 태그를 사용하고, 하단 원문 아코디언도 제품별로 그룹화하여 제공하도록 확정함.**
- **Q: 리랭킹 문서 선별과 LLM 토큰 생성 과정에 Top-P(누적 질량 필터링) 방법론을 어떻게 이중(2-Stage)으로 도입할 것인가?** → **A: 2단계 통합 Top-P(2-Stage Top-P) 아키텍처 확정. (1) [문서 리랭킹 단계]: BGE-Reranker 점수 0.35 이상 후보군을 확률 정규화(Softmax/Linear Mass)한 뒤 누적 관련도 80~85% 구간까지의 문서만 가변 선별하는 '문서 동적 Top-P (Document Nucleus Selection)' 및 급격한 점수 급락(Score Cliff > 0.25) 조기 컷오프를 적용함. (2) [토큰 생성 단계]: Qwen 3.5 모델 생성 파라미터에 `top_p=0.85`, `temperature=0.3`, `repetition_penalty=1.05`를 적용하여 RAG 사실성(Factuality)과 한국어 유려함을 극대화함.**
- **Q: 멀티턴 대화 중 이전 대화 이력을 회상(Deep Recall)할 때, 이전 턴에서 인용되었던 리뷰와 현재 턴에서 새로 검색된 리뷰의 인용 번호가 충돌하지 않도록 어떻게 구분 표기할까요?** → **A: Option A 확정. 현재 턴에서 새로 검색된 최신 리뷰는 `[리뷰 1]`, `[리뷰 2]`로 기본 부여하고, 이전 턴 회상 문맥은 `[Turn N 리뷰 1]` 형태로 턴 번호 접두사를 명시하여 완전히 분리 표기하도록 확정함.**
- **Q: 기술 실증/시연 환경에서 타임아웃, 진행 피드백, 중단 및 오류 처리 정책을 어떻게 규격화할 것인가?** → **A: 개발/실증용(Dev/POC) 모드 기준 넉넉한 타임아웃(Inactivity 45s, Total 180s) 적용, 실제 파이프라인 단계 전이에 기반한 실시간 진행 표시기(눈속임 배제), 사용자 주도 즉시 생성 중단(Stop) 기능 및 서버 에러 발생 시 정직한 투명 고지 체계 구축 확정.**
- **Q: 규칙 기반 처리와 LLM 처리의 상호 보완 및 LangGraph 도구화를 어떻게 결합할 것인가?** → **A: 전 단계 2중 하이브리드 결합 및 LangGraph 도구화 확정. (1) 전처리/검색/후처리 전 단계에 걸쳐 Python 규칙의 속도/결정론과 LLM의 문맥 이해를 결합하여 상호 보완. (2) 상품 검색(`tool_search_catalog`), 리뷰 추출(`tool_get_reviews`), 스펙 조회(`tool_get_specs`)를 LangGraph 표준 도구로 캡슐화하여 고속 실행과 에이전틱 확장성을 동시 확보함.**

## 2. User Scenarios & Testing *(mandatory)*

### User Story 1 - ChatA/ChatB 리뷰 인용 출처(Citation) 표기 무결성 및 상호보완형 하이브리드 질의 정규화 (Priority: P1)

화장품 구매를 고민 중인 소비자가 특정 제품명과 원하는 속성을 포함하여 자연어로 질문할 때, 챗봇은 상호보완형 하이브리드 파서를 통해 올바른 상품을 검색하고, 문서 동적 Top-P로 엄선된 실제 구매자 리뷰 번호(`[리뷰 1]`, `[리뷰 2]`)를 본문에 명확히 인용 표기하며 하단에 일치하는 리뷰 원문을 제공해야 합니다.

- **Why this priority**: 리뷰 기반 화장품 AI 챗봇의 핵심 가치는 "실제 구매자 후기에 기반한 신뢰성"에 있으며, 출처 없는 허위 주장이나 인용 누락은 서비스 신뢰도를 치명적으로 훼손하기 때문입니다.
- **Independent Test**: "컬러그램 탕후루 탱글 꿀로스의 발림성 장단점을 분석해줘" 및 "닥터자르트 시카페어 진정 크림의 진정 장단점" 질의 시, 상품명이 정확히 추출되어 관련 리뷰들이 수집되고, 답변 본문 각 단락에 `[리뷰 1]`, `[리뷰 2]` 등의 인용 태그가 붙으며 하단 아코디언에 동일한 원문이 펼쳐지는지 검증합니다.

**Acceptance Scenarios**:
1. **Given** 복합 자연어 질문(예: "롬앤 쥬시 래스팅 틴트 지속력 어때?")이 입력되었을 때, **When** 시스템이 하이브리드 파서로 정규화하면, **Then** 상품명(`롬앤 쥬시 래스팅 틴트`)과 분석 속성(`지속력`)이 정확히 분리되어 최소 1건 이상의 실제 리뷰가 검색되어야 합니다.
2. **Given** 실제 리뷰가 5건 선별되어 답변이 생성될 때, **When** 사용자가 답변을 읽으면, **Then** 만족스러운 점과 아쉬운 점 본문마다 관련된 리뷰 인용 번호(예: `[리뷰 1]`, `[리뷰 3]`)가 본문에 반드시 포함되어야 하며, 하단 `📚 참조 리뷰 원문 (5건 선별)` 아코디언의 각 리뷰 번호/평점/옵션 정보와 1:1로 정확히 일치해야 합니다.

## 3. User Story 2 - 카테고리/속성 추천(Discovery) 자동 발굴 및 제로 서치 환각 방지 (Priority: P2)

특정 상품명이 지정되지 않은 카테고리 추천 질문(예: "민감성 피부 쿠션팩트 추천해줘")에 대해 시스템은 LangGraph 도구를 통해 DB 내 실존 인기 상품 3~5개를 자동 발굴하여 실제 리뷰 기반으로 비교 추천하고, 매칭되는 데이터가 전혀 없는 경우 거짓 리뷰를 지어내지 않고 검색 결과가 없음을 솔직하게 안내해야 합니다.

- **Why this priority**: 사용자의 자연스러운 탐색형 질문(Discovery)을 처리하고, 데이터가 없는 상황에서 가짜 리뷰나 무의미한 문장("이 제품은...", "안녕하세요? 순하고")을 창작하는 환각(Hallucination)을 원천 차단하기 위함입니다.
- **Independent Test**: (1) "민감성 피부에 좋은 쿠션팩트 있나요" 질문 시 상위 3개 쿠션팩트가 발굴되어 각 제품별 실제 리뷰와 함께 추천되는지 검증, (2) 가상 상품("외계인 은하수 수분크림") 질문 시 허위 리뷰 없이 100% 정직한 부재 안내 메시지를 반환하는지 검증합니다.

**Acceptance Scenarios**:
1. **Given** 카테고리/속성 추천 질문이 입력되었을 때, **When** 라우터가 이를 `FEATURE_DISCOVERY`로 감지하면, **Then** DB에서 카테고리와 속성에 부합하는 상위 3~5개 실존 상품을 자동 인출하고 각 상품별 실제 리뷰(`[제품A 리뷰 1]`, `[제품B 리뷰 1]`)를 인용하여 비교 추천해야 합니다.
2. **Given** 1차 및 2차 재구성 검색 결과가 0건이거나 리랭킹 점수 0.35 미만일 때, **When** 답변이 생성되면, **Then** "현재 올리브영에 등록된 실제 구매자 리뷰를 찾을 수 없습니다"라는 정직한 안내 메시지를 표시하고 가짜 사용자 평이나 임의의 리뷰 인용을 절대 생성하지 않아야 합니다.

## 4. User Story 3 - 2단계 Top-P, 실증 데모 타임아웃/피드백 및 게이트웨이 연동 표준화 (Priority: P3)

A-Team 및 B-Team 서비스는 2단계 Top-P 필터링과 함께 실증 데모 친화적 타임아웃(Dev 모드 넉넉한 기준)과 투명한 파이프라인 상태 피드백, 사용자 생성 중단(Stop) 기능 및 서버 에러 정직 안내를 제공해야 합니다.

- **Why this priority**: GTX 1070 실증 환경에서 프리필 지연으로 인한 오작동을 방지하고, 사용자에게 눈속임 없는 실시간 진척도와 통제권을 부여하기 위함입니다.
- **Independent Test**: (1) Dev 모드에서 45초 무응답까지 안정 대기하며 실제 파이프라인 단계가 UI에 실시간 반영되는지 검증, (2) 사용자가 '생성 중단' 클릭 시 즉시 리소스가 해제되는지 검증, (3) 서버 장애 시 명확한 에러 메시지가 출력되는지 검증합니다.

**Acceptance Scenarios**:
1. **Given** GTX 1070에서 긴 프롬프트 프리필이 진행될 때, **When** 시스템이 동작하면, **Then** '의도 분석 $\rightarrow$ 검색 $\rightarrow$ 리랭킹 $\rightarrow$ 답변 생성' 실제 파이프라인 단계가 UI에 실시간 표시되고 45초 무응답 타임아웃 이내에 안정적으로 스트리밍이 개시되어야 합니다.
2. **Given** 긴 답변 생성이 진행 중일 때, **When** 사용자가 '중단' 버튼을 누르면, **Then** 백엔드 SSE 연결이 즉시 종료되고 화면에 "사용자에 의해 생성이 중단되었습니다"가 표시되어야 합니다.
3. **Given** 모델 서버 장애 또는 네트워크 단절 발생 시, **When** 파이프라인이 중단되면, **Then** 무한 대기하지 않고 "서버 응답 오류: 모델 게이트웨이와의 연결이 끊어졌습니다"와 같은 명확한 안내를 표시해야 합니다.

## 5. Edge Cases

- **EC-001 (품목명 내 속성어 충돌 및 신조어)**: "닥터자르트 시카페어 진정 크림"처럼 상품명에 속성어가 포함된 경우, Kiwi Fast-Path 후방 절단 및 Qwen 2B SLM 중재자가 카탈로그와 대조하여 상품명 훼손을 원천 방지.
- **EC-002 (타겟 제품이 2개 이상인 비교 질문)**: "A틴트랑 B글로스 비교해줘" 질의 시, 두 제품의 검색 결과가 각각 3건, 0건인 경우 A제품에 대해서만 `[A 제품 리뷰 1]`을 인용하고 B제품은 리뷰 부재 상태를 명확히 분리 고지.
- **EC-003 (급격한 점수 급락 - Score Cliff)**: 1위 리뷰 점수가 0.95이고 2위 리뷰 점수가 0.45로 급락(Drop > 0.25)하는 경우, 누적 Top-P 도달 전이라도 1위 리뷰만 단독 채택하여 품질 저하를 방지.
- **EC-004 (기형 인용 태그 생성)**: LLM이 `[1]` 또는 `[리뷰 1, 2]` 등으로 축약 출력할 경우, Python 인용 후처리기 가드레일이 `[리뷰 1]`, `[리뷰 2]`로 자동 정규화하여 UI 아코디언 매핑 유지.
- **EC-005 (프리필 중 사용자 이탈 또는 중단)**: 사용자가 스트리밍 도중 브라우저를 닫거나 '중단'을 누른 경우, SSE 소켓을 즉시 닫고 GPU 추론 세마포어를 즉각 반환하여 서버 자원 낭비 방지.

## 6. Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (하이브리드 캐스케이디드 질의 파서)**: 챗봇 전처리 엔진은 Stage 1 Kiwi 형태소 Fast-Path(<3ms)로 1차 정규화 및 카탈로그 매칭을 수행하고, 0건 또는 모호성 감지 시 Stage 2 Qwen 2B SLM 구조화 분석(<60ms)으로 Fallback하여 교차 검증 Grounding을 수행해야 한다.
- **FR-002 (LangGraph 코어 도구화)**: 상품 카탈로그 검색, 리뷰 추출, 기본 스펙 조회를 재사용 가능한 Typed LangGraph Tool(`tool_search_catalog`, `tool_get_reviews`, `tool_get_specs`)로 캡슐화해야 한다.
- **FR-003**: 카테고리/속성 추천 질의(예: "민감성 피부 쿠션팩트")에 대해 라우터는 `FEATURE_DISCOVERY` 패턴으로 분류하고, LangGraph 도구를 통해 DB 상위 평점 실존 제품 3~5개를 자동 발굴(Discovery)해야 한다.
- **FR-004 (문서 동적 Top-P)**: 리랭킹 노드는 검색된 리뷰 중 $s_i < 0.35$ 저품질 문서를 1차 컷오프한 후, 남은 문서들의 관련도 점수를 확률 분포화하여 누적 관련도 질량 $P_{\text{doc}} \ge 0.80 \sim 0.85$ 구간의 문서만을 가변 선별(최소 1건, 최대 15건)해야 한다.
- **FR-005 (점수 절벽 조기 차단)**: 인접 문서 간 관련도 점수 차이가 0.25 이상 급락(Score Cliff)하는 경우, 하위 노이즈 문서 유입을 방지하기 위해 해당 지점에서 문서 선별을 조기 절단해야 한다.
- **FR-006**: 컨텍스트 조립 노드는 문서 Top-P를 통과한 리뷰마다 고유한 순위 번호(`rank="1"`, `rank="2"`)와 제품 식별자를 부여하여 LLM에 전달해야 한다.
- **FR-007**: LLM 생성 시스템 프롬프트는 답변 본문의 모든 장단점, 속성 평가, 사용자 반응 서술 시 단일 제품은 `[리뷰 1]`, `[리뷰 2]`, 복수 제품은 `[제품명A 리뷰 1]`, `[제품명B 리뷰 1]`, 회상 문맥은 `[Turn N 리뷰 M]` 형태의 인라인 인용 부호를 명기하도록 엄격히 강제해야 한다.
- **FR-008 (인용 태그 가드레일)**: Python 후처리 엔진은 LLM이 생성한 본문의 인용 부호를 검증하고 기형 태그(`[1]`, `[리뷰 1, 2]`)를 표준 포맷으로 자동 정규화해야 한다.
- **FR-009**: 선별된 유효 리뷰가 0건인 경우, 시스템은 가짜 리뷰 창작 프롬프트를 차단하고 "실제 리뷰 데이터 부재" 안내를 명시적으로 출력하는 제로 서치 환각 방지 가드(Zero-Search Guard)를 적용해야 한다.
- **FR-010**: ChatA(Streamlit) 및 ChatB(FastAPI Web)의 사용자 인터페이스는 본문의 인용 번호(`[리뷰 N]` / `[제품명 리뷰 N]` / `[Turn N 리뷰 M]`)와 1:1로 대응되는 원문 펼쳐보기(아코디언/배지/상품 카드)를 제품별로 그룹화하여 상시 정확하게 렌더링해야 한다.
- **FR-011 (실증 모드 타임아웃 & 피드백)**: 시스템은 `ENVIRONMENT_MODE`에 따라 개발/실증 모드(Dev) 시 Sliding Inactivity Timeout을 45초, 총 타임아웃을 180초로 넉넉히 적용하고, 실제 파이프라인 상태를 UI에 실시간 표시해야 한다.
- **FR-012 (중단 및 투명 에러 통지)**: UI는 사용자 주도의 실시간 '생성 중단' 버튼을 제공하고, 서버 장애나 모델 응답 실패 발생 시 은폐 없이 명확한 원인 에러 메시지를 표시해야 한다.
- **FR-013**: A-Team 및 B-Team의 모든 LLM 클라이언트는 고정 Top-K 대신 최신 업계 표준인 Top-P Nucleus Sampling (`top_p: 0.85`, `temperature: 0.3`, `repetition_penalty: 1.05`) 파라미터를 요청 본문에 명시하여 전송해야 한다.

## 8. Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001 (하이브리드 질의 정규화 정확도)**: 신조어/속성명 충돌/오탈자 질의를 포함하여 상품명 정규화 및 카탈로그 매칭 성공률이 98% 이상이어야 한다.
- **SC-002 (리뷰 인용 무결성)**: 리뷰가 1건 이상 존재하는 정상 질의에 대해 본문 인용 표기(`[리뷰 N]` / `[제품명 리뷰 N]` / `[Turn N 리뷰 M]`) 및 하단 원문 아코디언/카드 노출 성공률이 100%여야 한다.
- **SC-003 (제로 서치 환각 방지)**: 데이터가 없는 상품 질의 시 허위 리뷰 창작율이 0%여야 하며, 정직한 부재 안내율이 100%여야 한다.
- **SC-004 (실시간 피드백 및 중단 반응성)**: 사용자의 '생성 중단' 클릭 시 500ms 이내에 스트리밍이 즉시 종료되고 GPU 자원이 반환되어야 한다.
- **SC-005 (장애 투명 고지율)**: 모델 서버 단절 등 실제 장애 발생 시 무한 로딩 없이 100% 명확한 에러 메시지가 출력되어야 한다.
- **SC-006 (전사 회귀 테스트 통과)**: 3대 챗봇(PILOS, ChatA, ChatB) 및 리포트 파이프라인의 통합 회귀 테스트가 100% 통과해야 한다.

## 9. Assumptions

- 올리브영 화장품 상품명 및 리뷰 데이터는 MySQL 및 ChromaDB에 적재되어 있다.
- 형태소 분석 및 명사 추출에는 `kiwi-nlp`가 사용되며, 브랜드/상품명 사전은 `alias_dictionary.py`를 통해 보정된다.
- Model Gateway는 `http://vllm-serv-gateway:8081` (로컬 포트 8081)에서 2B(64K) 상시 및 4B(32K) 배치 서비스를 안정 제공하고 있다.
