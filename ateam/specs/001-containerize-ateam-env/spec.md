## Clarifications

### Session 2026-08-17

- Q: A-Team 컨테이너와 기존 LLM 컨테이너 간의 네트워크 연결 방식을 어떻게 구성할까요? → A: 공통 Docker 사용자 정의 브리지 네트워크(사전 정의된 외부/공유 네트워크)를 생성하여 컨테이너 이름(DNS)으로 직접 통신
- Q: A-Team의 외부 서비스 기본 포트(Web 대시보드 및 DBMS)를 몇 번 포트로 기본 할당할까요? → A: Web: `8080`, MySQL: `3307` 기본 할당 (`.env`로 변경 가능)
- Q: 2.6GB 크기의 대용량 DB 덤프(`pilos_v2.sql`)의 복원 및 초기화 절차를 어떻게 구성할까요? → A: 1회성 DB 초기화 스크립트/프로필을 통해 덤프 적재 완료를 확인한 후 웹 서비스를 안정적으로 기동하는 단계별 워크플로우 구성

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A-Team 웹 애플리케이션 및 DBMS 컨테이너 환경 구동 및 데이터 복원 (Priority: P1)

개발자 및 운영자는 마이그레이션된 소스 코드와 대용량 데이터베이스 덤프 파일(`pilos_v2.sql`)을 신규 개발 플랫폼(Windows 11 + WSL2 + Rancher Desktop) 상에서 컨테이너 기반으로 구동하고, 데이터 손실 없이 기존 데이터를 온전히 조회하고 웹 서비스를 이용할 수 있어야 합니다.

**Why this priority**: 프로젝트의 핵심 비즈니스 로직 및 기존에 적재된 감성 분석/수집 데이터에 정상 접근할 수 있어야 전체 서비스의 최소 기능 제품(MVP) 동작이 가능합니다.

**Independent Test**: 1회성 초기화 절차를 통해 DBMS 컨테이너 기동 및 덤프 데이터 적재를 완료한 후, A-Team 웹 애플리케이션 컨테이너를 실행하여 브라우저에서 메인 대시보드와 데이터 조회 기능이 정상 동작하는지 확인하여 독립적으로 검증할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 마이그레이션된 DB 덤프 파일과 프로젝트 소스 코드가 준비되어 있을 때, **When** 1회성 DB 초기화 스크립트/프로필을 실행하면, **Then** 대용량 덤프 데이터가 영속 볼륨에 오류 없이 적재되고 복원 완료 상태가 명확히 확인되어야 한다.
2. **Given** DBMS 컨테이너에 데이터 복원이 완료된 상태에서, **When** A-Team 웹 서비스 컨테이너를 기동하면, **Then** 애플리케이션이 DBMS에 성공적으로 연결되어 저장된 데이터를 화면에 표시해야 한다.
3. **Given** 컨테이너가 동작 중인 상태에서, **When** 컨테이너를 재시작하거나 중지 후 재기동했을 때, **Then** 별도의 덤프 재적재 과정 없이 영속 볼륨을 통해 기존 데이터가 100% 유지되어야 한다.

---

### User Story 2 - 컨테이너화된 LLM 추론 서버 연동 (Priority: P2)

A-Team 웹 서비스 컨테이너는 별도의 컨테이너로 동작 중인 LLM 추론 및 임베딩 서버와 공통 Docker 브리지 네트워크를 통해 원활히 통신하여 감성 분석, 챗봇 대화 질의 및 보고서 생성 기능을 수행할 수 있어야 합니다.

**Why this priority**: LLM 질의는 A-Team 감성 지수 분석 및 챗봇 리포트 서비스의 핵심 부가가치 기능으로, 웹/DB 기본 동작 후 필수적으로 연결되어야 합니다.

**Independent Test**: A-Team 서비스 내 챗봇 또는 감성 분석 요청 기능을 실행하여 LLM 컨테이너로부터 올바른 응답을 수신하고 화면에 표출하는지 확인함으로써 독립 검증할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** LLM 서버 컨테이너가 공통 Docker 네트워크에 연결되어 있을 때, **When** A-Team 서비스에서 텍스트 분석 또는 챗봇 질의를 요청하면, **Then** A-Team 컨테이너가 DNS(컨테이너 이름) 기반으로 LLM 컨테이너와 통신하여 정상적으로 분석 결과를 반환받아야 한다.
2. **Given** LLM 서버와의 연결 정보(엔드포인트 주소, 포트, 타임아웃 등)가 변경되었을 때, **When** 환경 설정을 업데이트하고 서비스를 재기동하면, **Then** 소스 코드 변경 없이 새로운 LLM 엔드포인트와 통신이 이루어져야 한다.

### User Story 3 - B-Team과의 포트 충돌 방지 및 독립적인 외부 서비스 라우팅 구성 (Priority: P3)

동일한 호스트 머신에서 B-Team의 컨테이너 서비스가 이미 구동 중인 상태에서, A-Team의 웹 서비스(기본 `8080`)와 DBMS(기본 `3307`)는 B-Team의 점유 포트와 충돌하지 않는 독립 포트를 할당받아 외부 클라이언트에게 무중단으로 서비스를 제공할 수 있어야 합니다.

**Why this priority**: 외부 사용자 및 평가자가 A-Team과 B-Team 서비스를 간섭 없이 동시에 접근하여 사용할 수 있도록 인프라 네트워크를 안정적으로 격리해야 합니다.

**Independent Test**: B-Team 서비스가 실행 중인 상태에서 A-Team 서비스를 동시 구동한 뒤, 외부 브라우저에서 각각 지정된 포트로 접속하여 양쪽 서비스가 충돌 없이 동시에 응답하는지 검증합니다.

**Acceptance Scenarios**:

1. **Given** B-Team의 웹 서비스가 호스트의 특정 포트를 점유하고 있을 때, **When** A-Team 컨테이너를 기동하면, **Then** 포트 바인딩 충돌 없이 기본 Web `8080`, MySQL `3307` 포트로 서비스가 정상 오픈되어야 한다.
2. **Given** A-Team과 B-Team 컨테이너가 모두 실행 중일 때, **When** 외부 클라이언트가 각 팀의 고유 접속 포트(예: A-Team Web `8080`)로 HTTP 요청을 전송하면, **Then** 각 팀의 서비스가 상호 간섭 없이 독립적인 응답을 반환해야 한다.

---

### Edge Cases

- **대용량 DB 덤프 초기화 타임아웃**: 2.6GB 이상의 대용량 SQL 파일 적재 시 1회성 초기화 워크플로우를 분리하여 컨테이너 재시작 루프나 헬스체크 타임아웃을 방지합니다.
- **LLM 컨테이너 일시적 응답 지연/장애**: LLM 서비스 컨테이너가 재기동 중이거나 과부하 상태일 때, A-Team 웹 애플리케이션이 크래시되지 않고 적절한 오류 안내 및 재시도 처리를 수행해야 합니다.
- **호스트 포트 충돌 예외**: 지정된 기본 서비스 포트(`8080` / `3307`)가 다른 프로세스에 의해 이미 사용 중일 경우, 환경 설정을 통해 포트를 즉시 변경하여 실행할 수 있어야 합니다.
- **WSL2 / Windows 파일 시스템 권한 및 경로 이슈**: 윈도우 호스트 파일 시스템과 WSL2 컨테이너 간의 볼륨 마운트 시 권한 에러나 성능 저하가 발생하지 않도록 적절한 경로 및 볼륨 구조를 유지해야 합니다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 2.6GB 대용량 DB 덤프 파일(`pilos_v2.sql`)을 타임아웃 없이 안전하게 복원할 수 있는 1회성 초기화 워크플로우(스크립트/프로필)를 제공해야 합니다.
- **FR-002**: 시스템은 A-Team 웹 애플리케이션을 컨테이너 이미지로 빌드하고 독립적인 컨테이너로 안정적으로 기동할 수 있어야 합니다.
- **FR-003**: 시스템은 A-Team 애플리케이션 컨테이너에서 DBMS 컨테이너로의 내부 네트워크 연결을 안정적으로 유지해야 합니다.
- **FR-004**: 시스템은 사전 정의된 공통 Docker 브리지 네트워크를 통해 LLM 컨테이너와 A-Team 컨테이너를 연결하고, 컨테이너 이름(DNS) 기반으로 통신을 수행해야 합니다.
- **FR-005**: 시스템은 B-Team 및 로컬 프로세스와의 포트 충돌을 방지하기 위해 기본 외부 노출 포트를 Web `8080`, MySQL `3307`로 할당하고, 필요 시 `.env` 환경 변수를 통해 유연하게 재지정할 수 있어야 합니다.
- **FR-006**: 시스템은 컨테이너가 재시작되거나 재빌드되어도 데이터베이스의 데이터가 영구적으로 보존되도록 볼륨 영속성을 보장해야 합니다.
- **FR-007**: 시스템은 Windows 11 + WSL2 + Rancher Desktop 환경에서 단일 명령 또는 표준 스크립트를 통해 전체 컨테이너 환경(Web + DBMS)을 일관되게 배포 및 관리할 수 있어야 합니다.

### Key Entities

- **A-Team Web Application Container**: 감성 분석 지표 시각화, 수집 데이터 조회, 챗봇 및 리포트 인터페이스를 제공하는 메인 서비스 컨테이너
- **A-Team DBMS Container**: `pilos_v2.sql` 데이터가 적재되어 영속 볼륨과 연동되는 관계형 데이터베이스 컨테이너
- **LLM Serving Container**: 독립된 컨테이너 환경에서 텍스트 추론, 임베딩, 감성 분석 API를 제공하는 공용 AI 엔진 엔티티
- **Network & Port Configuration**: B-Team 포트와의 충돌을 피하고 외부 및 컨테이너 간 통신을 라우팅하는 네트워크 구성 정의체

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 마이그레이션된 DB 덤프의 테이블 및 데이터가 100% 누락 없이 신규 DBMS 컨테이너에 정상 복원되어야 합니다.
- **SC-002**: 외부 클라이언트가 지정된 웹 포트(`http://localhost:8080`)로 접속 시 3초 이내에 A-Team 메인 서비스 화면이 정상 렌더링되어야 합니다.
- **SC-003**: A-Team과 B-Team 컨테이너 서비스가 단일 호스트 머신에서 포트 충돌 없이 동시에 100% 정상 구동 및 외부 접근이 가능해야 합니다.
- **SC-004**: A-Team 서비스에서 요청한 LLM 기반 챗봇 질의 및 분석 작업이 정상 처리되어 5초 이내에 첫 응답 스트림 또는 결과를 반환해야 합니다.
- **SC-005**: 컨테이너 중지 및 재기동 후에도 데이터베이스 내 데이터 및 설정의 100% 보존이 확인되어야 합니다.

## Assumptions

- 대상 개발 환경에는 Windows 11, WSL2, Rancher Desktop(Docker CLI / Compose 호환 런타임)이 정상적으로 설치 및 설정되어 있습니다.
- LLM 서비스 컨테이너는 동일 머신 또는 접근 가능한 네트워크 상에서 사전 합의된 포트로 이미 구동 중이거나 실행 가능한 상태입니다.
- B-Team 서비스는 특정 외부 포트(예: 표준 포트 등)를 점유하고 있으므로, A-Team 서비스는 중복되지 않는 별도의 전용 포트 대역(Web 8080, DB 3307)을 기본 할당합니다.
- 데이터베이스 비밀번호, API 키, 외부 엔드포인트 등 민감정보는 `.env` 환경 변수를 통해 안전하게 주입받아 관리합니다.
