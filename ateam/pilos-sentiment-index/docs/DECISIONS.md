# 설계 결정 기록 (DECISIONS)

> 정본 범위: 프로젝트 진행 과정에서 합의된 주요 설계 결정과 변경 이력을 기록합니다.
>
> 상태: 현재 기준
>
> 최초 적용일: 2026-07-25
>
> 마지막 갱신: 2026-08-10

---

# 1. 문서 목적

이 문서는 프로젝트에서 **왜 이러한 구조와 규칙을 선택했는지** 기록하기 위한 문서입니다.

프로젝트가 진행되면서 구조는 계속 변경될 수 있습니다.

하지만 변경된 결과만 남기면 시간이 지나 다음과 같은 질문이 반복됩니다.

- 왜 이렇게 구현했는가?
- 왜 이 구조를 선택했는가?
- 왜 예전 방식은 사용하지 않는가?
- 다시 이전 구조로 돌아가도 되는가?

이 문서는 이러한 설계 배경을 기록하여 같은 논의를 반복하지 않도록 하는 것을 목적으로 합니다.

---

# 2. 작성 원칙

이 문서에는 **구현 방법**을 기록하지 않습니다.

다음 내용을 기록합니다.

- 어떤 결정을 했는가
- 왜 그렇게 결정했는가
- 어떤 영향을 받는가
- 이후 변경되었는가

구현 코드와 사용 방법은 각각의 문서에서 관리합니다.

| 문서 | 역할 |
|------|------|
| ARCHITECTURE | 시스템 구조 |
| DATA_CONTRACT | 데이터 규칙 |
| GIT_WORKFLOW | Git 운영 규칙 |
| DECISIONS | 설계 이유와 변경 기록 |

---

# 3. 상태 구분

각 결정은 다음 상태 중 하나를 가집니다.

| 상태 | 의미 |
|------|------|
| 결정 완료 | 프로젝트 기준으로 선택한 방향 |
| 실험 기본값 | 첫 연결과 비교를 위해 현재 사용하는 값이며 최종 결정은 아님 |
| 보류 | 증거 또는 구현이 부족해 아직 확정하지 않음 |
| 대체됨 | 새로운 결정으로 교체되어 현재 기준으로 사용하지 않음 |

결정 상태와 구현·검증 상태는 별개입니다. 코드가 존재한다는 이유만으로 결정 완료로 기록하지 않고, 결정이 완료됐다는 이유만으로 구현 완료나 검증 완료로 기록하지 않습니다.

저장 여부는 실행 흐름에서 결정합니다.

---

## 기대 효과

- 테스트 용이

# D-008 TF-IDF 토큰 처리 역할

**결정 상태**

결정 완료

**구현 상태**

`develop` 적용 완료

**검증 상태**

네 종류의 일별 TF-IDF 검수 산출물 확인

---

## 결정

- 형태소의 `form`을 TF-IDF feature 단위로 사용합니다.
- 품사 `tag`는 feature 문자열에 포함하지 않습니다.
- 형태소 분석기가 토큰을 결정합니다.
- TF-IDF 입력은 형태소 `form`을 공백으로 연결한 문자열입니다.
- 하나의 `form` 내부 공백은 `_`로 치환합니다.
- sklearn 기본 tokenizer에 의존하지 않습니다.
- `TfidfVectorizer`는 벡터화와 TF-IDF 가중치 계산을 담당합니다.
- 훈련 데이터에는 `fit_transform`, 검증·추론 데이터에는 학습된 vectorizer의 `transform`만 사용합니다.

현재 `develop`의 `vectorizer.py`에는 `tokenizer=str.split`,
`token_pattern=None`이 반영되어 있습니다.

`lowercase`는 vectorizer 내부에서 고정하지 않고 실행기가 전달합니다. 현재 모델 학습 기준선은 `lowercase=True`입니다.

# D-009 웹 요청 조합은 service

**결정 상태**

결정 완료

---

## 결정

Flask route는 HTTP 입력 확인과 응답 렌더링에 집중합니다.

분석 요청과 저장 결과 조회처럼 여러 영역이 필요한 웹 사용 사례는 `service`가 조합합니다.

`service`는 필요한 `storage`, `analysis`, `dto`를 호출하지만 모델 계산과 저장 입출력을 직접 구현하지 않습니다.

---

## 결정 이유

route가 저장 형식, 모델 구성요소와 DTO 변환까지 알게 되면 웹과 분석의 변경이 서로 강하게 연결됩니다.

웹 요청의 조합 책임을 분리하면 route를 가볍게 유지하고 같은 사용 사례를 재사용하기 쉽습니다.

# D-012 해석 가능한 Ridge 모델을 기준선으로 사용

**결정 상태**

대체됨 (`D-015`)

**구현 상태**

과거 기준선 구현 이력 보존, 현재 서비스 계약은 `D-015`로 대체

**검증 상태**

기준선 학습·검증 지표 확인, 일반화 성능 개선 필요

---

## 결정

초기 기준선은 다음 특성을 결합한 Ridge 회귀였습니다.

```text
TF-IDF
+ 표준화된 log1p(comment_count)
```

이 모델은 일반적인 긍정·부정 감정 분류기가 아니라 댓글의 단어와 활동량이 개인투자자 거래우위와 보이는 연관성을 학습합니다.

---

## 결정 이유

Ridge는 희소한 TF-IDF 입력을 처리하면서 각 단어의 계수를 유지하므로 예측값뿐 아니라 단어별 방향과 기여도를 설명할 수 있습니다.

프로젝트가 모델을 단순 예측기보다 해석 가능한 단어 사전처럼 활용하려는 목적과 맞습니다.

---

## 영향

Ridge를 해석 가능한 모델로 사용하는 결정은 유지합니다. 다만 댓글 수
특성을 포함한 초기 입력 계약은 후보 비교 결과에 따라 `D-015`의
text-only v4로 대체됐습니다.

- 초기 등록·보정용 일회성 도구는 `jobs/maintenance`에 두고 자동 운영에서 제외합니다.
- 제품 코드 아래 있던 수집 테스트는 `tests/collection`, 실험 Notebook은
  `notebooks/pipeline`과 `notebooks/llm`에 둡니다.
- 완료된 담당자 작업 문서는 `docs/work/archive`로 이동하되 Git 이력을 유지합니다.

## 결정 이유

기능 구현이 완료된 저장소에서 같은 계층에 운영 코드·외부 client·실험·테스트·일회성
도구가 섞여 있던 상태를 정리하고, 새 추상 계층 없이 현재 책임과 운영 여부를 경로만으로
구분하기 위함입니다.

# E-001 Kiwi 토큰화

**상태**

실험 기본값

---

Kiwi, 현재 품사 필터와 사용자 사전은 첫 분석 연결을 위한 실험 기본값입니다.

- Kiwi 사용 코드 존재
- 품사 필터 존재
- 사용자 사전 존재
- 토큰화 결과의 DB `tokenized_comment` 적재 구현
- 로컬 JSONL 검수 산출물 사용 가능

최종 형태소 분석기, 최종 품사 범위와 사용자 사전 관리 방식은 비교·검증 전까지 결정 완료로 올리지 않습니다.

현재 서비스 모델 v4는 `tokenizer_version=kiwi_ver1`로 학습됐으므로 해당
모델 추론에는 같은 토큰 계약을 사용합니다. 토크나이저를 변경하면 기존
v4를 수정하지 않고 새 모델 버전으로 재학습합니다.

# E-002 TF-IDF 실험값

**상태**

실험 기본값

---

다음 값은 최종 결정이 아니라 비교 가능한 실험값입니다.

- `lowercase=True`
- `ngram_range=(1, 1)`
- `min_df=5`
- `max_df=0.95`
- `max_features=None`
- `sublinear_tf=True`

unigram과 unigram·bigram 조합을 같은 Dataset과 평가 조건에서 비교한 뒤 최종값을 결정합니다.

서비스 모델 v4에는 `ngram_range=(1, 1)`, `min_df=5`, `max_df=0.95`,
`max_features=None`, `sublinear_tf=True`가 고정돼 있습니다. 이는 v4 재현
계약이며 이후 모델 버전의 후보 비교를 막는 영구 전역 결정은 아닙니다.

# P-001 토큰 저장 여부

## 현재 상황

현재 실행 기준선은 `kiwi_tokens`를 토크나이저 버전과 함께 DB

---

## 결정 이유

토큰화와 일별 문서 생성 사이에 재실행 가능한 경계를 두고, 사용한
토크나이저 버전과 처리 여부를 DB에서 추적하기 위함입니다. 실시간
처리에서도 같은 DB 중간 저장을 유지할지는 통합 파이프라인에서
재실행·복구 요구와 함께 판단합니다.
