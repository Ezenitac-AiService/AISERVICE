# 손성욱 프론트엔드 마무리 작업 확정 지시 및 검수 기준

> 현재 상태: `적용 완료`. 검색·최근 조회·목록·상세·v13·단일 댓글·챗봇과
> 파이프라인 상태 화면이 PR #15로 `develop@c387300`에 반영됐습니다. 아래
> 문서는 검수 이력이며 현재 계약은 `specs/sentiment-flask-web-integration.md`와
> `specs/chatbot-service.md`를 사용합니다.

> 담당 범위: Flask API 응답을 사용하는 화면 표시와 사용자 상호작용
>
> 문서 성격: Flask v13·단일 댓글·챗봇 확정 계약을 프론트에 연결하기 위한 작업 지시이자 결과 검수 기준
>
> 코드 확인 기준: `develop` (`c387300`, PR #15 프론트 계약 병합 완료)
>
> 최종 갱신일: 2026-08-10

## 1. 작업 목표

기존 프론트 화면을 폐기하거나 처음부터 다시 만들지 않는다. 현재 구현된 검색·목록·상세,
최근 조회, 정렬·필터와 예외 처리를 보존하면서 Flask가 확정해 제공하는 v13 데이터 계약에
맞춰 응답 처리와 표시 항목을 수정한다. 백엔드까지 완료된 단일 댓글 추론과 근거 기반
챗봇도 실제 사용자가 접근할 수 있는 화면으로 연결한다.

프론트는 DB나 API에 없는 값을 임의로 만들지 않는다. 모델 점수를 예측 정확도, 확률,
투자 신호나 미래 전망으로 다시 해석하지 않는다. 수급 방향, 신호 등급과 품질 상태는
Flask 응답을 그대로 사용한다.

## 2. 이번 문서 갱신 이유

이 문서는 처음에는 Flask 계약 확정 전 회의용 논의서였다. PR #10에서 Flask 계약이,
PR #12에서 챗봇 API와 service가 `develop`에 반영됐다. 작업자가 과거 camelCase 응답,
구형 LLM 보고서 또는 챗봇 병합 전 범위를 기준으로 구현하지 않도록 전체 프론트 작업
지시와 검수 기준으로 갱신한다.

| 갱신 항목 | 수정 이유 |
|---|---|
| 기준 커밋을 `d178211`로 변경 | PR #12 챗봇까지 병합된 최신 `develop`을 프론트 기준선으로 사용해야 함 |
| 공개 필드를 snake_case로 확정 | 기존 종목 API가 camelCase와 snake_case를 혼용했으나 Flask가 한 방식으로 통일함 |
| 품질·대기·오류 상태를 열거 | 모든 상태를 `데이터 없음`으로 합치면 사용자가 현재 처리 단계를 구분할 수 없음 |
| v13 보고서 필드를 확정 | 기존 화면이 더 이상 제공되지 않는 `scores`, `narrative`, 대표 댓글을 요구함 |
| 스냅샷 선택 책임을 Flask로 확정 | 프론트가 배열 순서로 정본을 선택하면 목록·상세·보고서가 다른 문서를 표시할 수 있음 |
| 내부 artifact 표시를 제거 | 일반 화면 API가 `artifact_id`를 더 이상 공개하지 않음 |
| 단일 댓글 화면을 필수 범위로 유지 | API와 실제 두 방향 모델 실행은 완료됐지만 이를 호출하는 화면이 없음 |
| 챗봇 화면과 공개 계약을 추가 | `/api/chat`과 route별 service는 병합됐지만 현재 HTML·JavaScript 호출부가 없음 |
| 챗봇 상태·출처 표시를 확정 | HTTP 성공 여부만 보면 근거 부족·미준비·외부 서비스 장애를 구분할 수 없음 |
| 결과물 검수표를 추가 | 작업 완료 여부를 코드 존재가 아니라 확정 API 소비와 화면 상태로 대조하기 위함 |

## 3. 작업 시작 브랜치

Flask 계약과 챗봇은 PR #10·#12로 `develop`에 반영됐다. 최신 `develop`을 기준으로 새 프론트
기능 브랜치를 만든다. 권장 이름은 `feature/frontend-v13-contract`다.

기존 `origin/feature/Frontend`는 최신 계약보다 오래됐으므로 그대로 이어서 병합하지 않는다.
디자인 의도나 누락 기능을 확인하는 참고 자료로만 사용한다. 과거 브랜치 코드를 복사할 때는
현재 `develop`의 검색·목록·상세·오류 처리를 덮어쓰지 않았는지 확인한다.

## 4. 유지할 현재 기능

특별한 이유 없이 다음 기능을 다시 작성하거나 제거하지 않는다.

- 종목명·종목코드 검색
- 최근 조회 종목의 브라우저 로컬 저장과 중복 제거
- 전체 종목 목록과 상세 화면 이동
- 목록 정렬·필터링
- 날짜별 추론 이력 이동
- API 로딩·빈 결과·오류·재시도 상태
- 여러 종목 조회 중 일부 요청 실패를 분리해 표시하는 처리
- 빠른 재조회 때 오래된 응답이 새 화면을 덮지 않게 하는 요청 세대 관리
- 사용자 문자열을 `textContent`로 넣는 기본 보안 처리
- 반응형 화면과 서비스 소개 화면

이번 작업은 데이터 계약 연결이 목적이다. 화면 전체 재설계나 공통 구조 대이동은 범위가
아니다.

## 5. 확정 Flask API 계약

### 5.1 공통 규칙

- 공개 JSON은 snake_case만 사용한다.
- 이전 camelCase 별칭을 프론트 내부 표준으로 남기지 않는다.
- 날짜와 관측 시각은 Flask가 전달한 ISO 문자열을 표시용으로만 변환한다.
- `null`을 `0`, `50`, 빈 문자열이나 임의 상태로 바꾸지 않는다.
- 내부 `artifact_id`, 입력 hash, provider 응답 ID와 토큰 사용량은 일반 화면에 표시하지 않는다.
- 종목·보고서·단일 댓글의 오류·대기 응답은 `status`와 `message`로 분기하고 메시지
  문자열을 상태 판정에 사용하지 않는다.
- 챗봇은 성공 응답의 `status`와 `route`, HTTP 오류 응답의 `error`를 사용한다. 챗봇의
  공개 오류 형식은 아래 별도 계약을 따른다.

### 5.2 종목 목록

```http
GET /api/stocks
```

응답은 등록 종목 전체의 배열이다. 일별문서나 활성 모델 결과가 없는 종목도 상태와 함께
포함될 수 있다.

| 필드 | 의미 |
|---|---|
| `stock_code`, `stock_name` | 종목 식별과 표시명 |
| `model_date`, `comment_count` | 최신 일별문서 기준일과 댓글 수 |
| `analysis_status` | 최신 문서의 현재 분석 상태 |
| `positive_model`, `negative_model` | 방향별 활성 모델 결과 또는 `null` |
| `actual_supply_demand_index` | 실제 개인 수급지수 |
| `actual_buy_volume`, `actual_sell_volume` | 개인 매수·매도량 |
| `supply_data_status` | `estimated`, `confirmed` 또는 `null` |
| `supply_observed_at` | 현재 수급값 관측 시각 또는 `null` |

### 5.3 종목 상세

```http
GET /api/stocks/<stock_code>
```

```json
{
  "stock_code": "000660",
  "stock_name": "SK하이닉스",
  "latest": {},
  "history": []
}
```

`latest`와 `history` 항목은 목록의 종목 항목과 같은 필드를 사용한다. `history`는 종목·날짜별
가장 큰 `daily_document_id`에 해당하는 최신 스냅샷 하나만 날짜 내림차순으로 반환한다.
프론트는 같은 날짜의 다른 정본을 다시 선택하지 않는다.

보고서 요청에는 사용자가 선택한 이력의 `model_date`만 전달한다. `daily_document_id`는
프론트 공개 계약이 아니며 화면에서 만들거나 보관하지 않는다.

### 5.4 방향별 모델 결과

`positive_model`과 `negative_model`은 결과가 있으면 다음 필드를 가진다.

```text
model_variant
supply_demand_association_score
intercept
text_score
comment_count_contribution
recognized_feature_count
unique_token_count
vocabulary_coverage
inference_status
positive_keywords
negative_keywords
```

키워드 항목은 `keyword`, `contribution`만 제공한다. TF-IDF 원값과 coefficient는 현재
Flask 공개 응답에 없으므로 화면에서 만들지 않는다.

품질 상태는 다음 우선순위로 Flask가 계산해 `analysis_status`에 전달한다.

```text
일별문서 없음                     → not_found
두 활성 artifact 중 결과 누락     → inference_pending
실제 수급 방향 없음               → no_direction
선택된 활성 결과의 DB 상태가 NULL → unknown
선택된 활성 결과 품질 부족        → insufficient_features
선택된 활성 결과 정상             → ready
```

BUY 수급은 Positive 결과, SELL 수급은 Negative 결과의 `inference_status`를 상위 품질
상태로 사용한다. 반대 방향 모델의 품질 부족을 근거로 상위 상태를 다시 낮추지 않는다.
DB NULL은 API에서만 `unknown`으로 표현하며 프론트도 다른 규칙으로 재판정하지 않는다.

### 5.5 저장된 v13 보고서

```http
GET /api/stocks/<stock_code>/llm-reports?model_date=YYYY-MM-DD
```

HTTP 200 보고서는 다음 필드를 사용한다.

```text
status
commentary_source
stock_code
stock_name
model_date
supply_direction
actual_supply_index
comment_signal_score
signal_level
signal_status
signal_change
signal_ma5
comment_count
market_commentary
conclusion
notice
report_supply_data_status
report_supply_observed_at
current_supply_data_status
current_supply_observed_at
report_refresh_status
```

`status`는 저장 보고서의 `ready` 또는 `insufficient_evidence`다.
`commentary_source`는 `llm` 또는 `deterministic`이다.

기존 estimated 보고서가 있고 현재 수급이 confirmed로 바뀌었지만 보고서 갱신이 아직
끝나지 않았다면 기존 보고서를 숨기지 않는다.

```text
report_supply_data_status = estimated
current_supply_data_status = confirmed
report_refresh_status = pending
```

화면은 이를 `확정 수급 반영 대기`처럼 구분하되 기존 보고서가 confirmed 기준이라고
오해하게 표시하지 않는다. `report_refresh_status=current`면 현재 수급 관측 상태와 보고서가
갱신 대기 상태가 아니다.

### 5.6 HTTP 상태와 오류 응답

| 조건 | HTTP | `status` | 화면 처리 |
|---|---:|---|---|
| 요청 JSON·날짜·필드 오류 | 400 | `invalid_request` | 사용자가 수정할 입력 오류 안내 |
| 종목·날짜의 일별문서 없음 | 404 | `not_found` | 빈 상태 표시 |
| 최신 문서의 활성 추론 미완료 | 202 | `inference_pending` | 추론 대기 표시 |
| 추론 완료, 보고서 미생성 | 202 | `report_pending` | 보고서 생성 대기 표시 |
| 현재 보고서 존재 | 200 | `ready` 또는 `insufficient_evidence` | 실제 보고서 표시 |
| DB·저장 JSON·내부 계약 오류 | 500 | `internal_error` | 재시도 가능한 서버 오류 안내 |

```json
{
  "status": "report_pending",
  "message": "활성 모델 추론은 완료됐지만 보고서 생성이 대기 중입니다."
}
```

### 5.7 챗봇

```http
POST /api/chat
Content-Type: application/json
```

프론트의 공식 요청은 자유 문장에서 종목·날짜·질문 종류를 다시 추측하지 않고 선택값을
명시적으로 전달한다.

```json
{
  "message": "확정 수급지수를 알려줘",
  "action": "stock_metric",
  "metric": "supply_demand_index",
  "stock_code": "000660",
  "model_date": "2026-08-08"
}
```

| 필드 | 규칙 |
|---|---|
| `message` | 비어 있지 않은 사용자 질문. 모든 요청에 필요 |
| `action` | `stock_analysis`, `stock_metric`, `service_knowledge` 중 하나 |
| `metric` | `stock_metric`에서만 사용. 아래 허용값 중 하나 |
| `stock_code` | 종목별 분석·수치 질문에서 선택한 종목코드 |
| `model_date` | 종목별 분석·수치 질문에서 선택한 `YYYY-MM-DD` 기준일 |
| `session_id` | 선택 필드. 현재 장기 대화 저장을 의미하지 않으며 화면에서 생략 가능 |

허용 metric은 다음 세 개다.

```text
supply_demand_index
individual_buy_volume
individual_sell_volume
```

질문 종류별 필수 문맥은 다음과 같다.

| `action` | 필수 선택값 | 사용 근거 |
|---|---|---|
| `stock_analysis` | 종목·기준일 | 저장된 현재 v13 보고서 |
| `stock_metric` | 종목·기준일·metric | MySQL의 confirmed 정확 수치 |
| `service_knowledge` | 질문 | 승인 서비스 문서 RAG |

`restricted`와 `general`은 사용자가 선택하는 action이 아니다. 투자 지시·미래 수익 보장·
비밀정보·내부 명령 요청은 서버 안전 검사에서 `restricted`로 전환될 수 있고, 지원 범위가
아닌 질문은 `general`로 응답할 수 있다.

HTTP 200 공개 응답은 다음 필드를 사용한다.

```text
status
answer
route
session_id
stock_code
as_of
sources
warnings
```

| `status` | 화면 의미 |
|---|---|
| `ready` | 정상 답변 또는 제한·지원 범위 안내 표시 |
| `needs_clarification` | 종목·날짜·metric 등 필요한 선택값 안내 |
| `not_ready` | 확정 수급·선행 추론·보고서 등 준비 대기 |
| `not_found` | 요청한 근거를 찾지 못함 |
| `unavailable` | DB·RAG·LLM 등 외부 단계 일시 사용 불가 |
| `failed` | 요청 처리 실패 |

`sources` 항목은 공개 필드만 표시한다.

```text
type       # mysql_metric, llm_report, service_document
label
version
stock_code
model_date
```

내부 chunk ID, 검색 점수, Chroma 경로와 collection 설정은 표시하지 않는다. `warnings`는
투자 권고가 아님과 근거 범위 제한을 사용자에게 전달하므로 답변과 함께 보여준다.

챗봇 요청 형식 오류는 HTTP 400과 `error`를 반환하며 허용되지 않은 action·metric에는
각각 `allowed_actions`, `allowed_metrics`가 함께 올 수 있다. 외부 service 호출 실패는
HTTP 503, 예상하지 못한 오류는 HTTP 500과 `error`를 반환한다. HTTP 200에서도 반드시
본문 `status`를 확인한다.

## 6. 파일별 필수 수정과 수정 이유

| 대상 | 필수 수정 | 수정 이유 |
|---|---|---|
| `pilos/web/static/js/common.js` | `positive_model`, `negative_model` 기준으로 모델 존재 여부 판정 | 기존 camelCase 판정은 새 API에서 항상 결과 없음으로 오인함 |
| `pilos/web/static/js/index.js` | 목록 필드 snake_case 연결, `analysis_status`·수급 상태 표시, `artifactId` 표시 제거 | 목록이 새 응답을 읽고 미분석 종목을 정상 종목과 구분해야 함 |
| `pilos/web/static/js/detail.js` | 상세·이력 필드 snake_case 연결, v13 보고서 렌더링, 202 상태 분리 | 현재 코드는 과거 LLM 구조와 `not_ready` 하나만 처리함 |
| `pilos/web/templates/detail.html` | artifact 영역과 과거 LLM 점수·대표 댓글 영역을 새 표시 항목으로 교체 | API에 없는 내부 ID와 과거 보고서 필드를 요구하고 있음 |
| `pilos/web/static/css/index.css` | 품질·수급·대기 상태 배지와 모바일 표시 보완 | 상태를 색상 하나나 빈 데이터로 합치지 않기 위함 |
| `pilos/web/static/css/detail.css` | v13 해설·결론·수급 갱신 상태와 단일 댓글 영역 스타일 보완 | 변경된 정보 구조를 PC·모바일에서 읽을 수 있어야 함 |
| 단일 댓글 UI 파일 | 입력, 로딩, 중복 제출 방지, 결과·오류 표시 추가 | API는 완료됐지만 이를 호출하는 화면이 현재 없음 |
| 챗봇 UI 파일 | 질문 종류·종목·날짜·metric 선택, `/api/chat` 호출, 답변·출처·warning·상태 표시 | 챗봇 백엔드는 완료됐지만 현재 HTML·JavaScript·CSS 호출부가 없음 |

파일을 새로 만들지 기존 화면에 넣을지는 현재 구조와 화면 배치에 맞춰 결정할 수 있다.
다만 단순 이름 정리를 이유로 공통 프론트 구조 전체를 재작성하지 않는다.

## 7. 화면 표시 규칙

### 7.1 목록

- 검색·최근 조회·정렬·필터를 유지한다.
- `analysis_status`를 사용자에게 이해 가능한 문구로 표시한다.
- `inference_pending`, `unknown`, `insufficient_features`를 정상 점수처럼 강조하지 않는다.
- `estimated`는 장중 추정, `confirmed`는 장마감 확정임을 배지 또는 보조 문구로 구분한다.
- Positive·Negative raw 점수를 감성 확률이나 예측 정확도로 표시하지 않는다.
- 현재 API가 목록에 `comment_signal_score`를 제공하지 않으므로 프론트에서 계산해 넣지 않는다.

### 7.2 상세과 날짜 이력

- `latest`를 첫 화면 기준으로 사용하고 `history`의 선택 날짜를 상세에 표시한다.
- 날짜별 이력은 Flask가 반환한 순서와 항목을 사용한다.
- 기존 `compareSupplyDirection()`과 `supplyComparisonLabel()`의 `실제 방향 일치·불일치`
  문구와 강조를 제거한다.
- 방향별 raw 결과를 유지한다면 `Positive 모델 결과`, `Negative 모델 결과`처럼 의미를
  구분하고 예측 성공 여부로 표현하지 않는다.
- `recognized_feature_count`, `unique_token_count`, `vocabulary_coverage`와 기여 키워드는
  상세 근거 영역에서 표시할 수 있다.

### 7.3 v13 보고서

- `market_commentary`, `conclusion`, `comment_signal_score`, `signal_level`을 중심으로 표시한다.
- 기존 `scores`, `narrative`, `representative_comments`, `evidence`, `technical_details`
  의존을 제거한다.
- `commentary_source=deterministic`은 실패한 LLM 응답처럼 표시하지 않고 정형 근거 기반
  요약임을 구분한다.
- `insufficient_evidence`는 근거 부족 보고서이며 일반 서버 오류와 구분한다.
- `notice`를 함께 표시해 투자 권고나 감성 확률로 해석하지 않게 한다.
- 보고서 수급 상태와 현재 수급 상태가 다르면 `report_refresh_status`를 함께 표시한다.

## 8. 단일 댓글 추론 화면

```http
POST /api/inference/single-comment
Content-Type: application/json

{"comment_text": "추가 매수한다"}
```

정상 응답은 다음 필드를 사용한다.

```text
comment_text
processed_text
token_count
positive_model
negative_model
notice
```

각 방향 결과는 `text_score`, `recognized_feature_count`, `positive_keywords`,
`negative_keywords`를 제공한다.

필수 화면 동작은 다음과 같다.

1. 댓글 한 건 입력과 전송
2. 빈 문자열 사전 안내와 서버 400 응답 처리
3. 요청 중 중복 제출 방지와 로딩 표시
4. Positive·Negative 결과를 서로 합치지 않고 각각 표시
5. `invalid_request`와 `internal_error` 구분
6. 단일 댓글 결과가 일별 공식 신호나 0~100 점수가 아니라는 `notice` 표시

입력 글자 수, 예시 문구와 화면 위치는 팀장과 조정할 수 있다. 다만 API 연결과 위 상태
구분은 이번 마무리 범위다.

## 9. 챗봇 화면

### 9.1 필수 화면 구성

1. 질문 종류 선택
2. 종목 질문일 때 종목 선택
3. 종목 질문일 때 상세 API의 이력에서 기준일 선택
4. 정확 수치 질문일 때 metric 선택
5. 질문 입력과 전송
6. 요청 중 중복 제출 방지와 로딩 표시
7. 답변·기준일·출처·warning 표시
8. 상태별 빈 화면·안내·재시도 처리

질문 종류의 사용자 문구와 요청값 예시는 다음처럼 연결한다.

| 화면 문구 | `action` | `metric` |
|---|---|---|
| 오늘 분석 요약 | `stock_analysis` | 없음 |
| 확정 수급지수 | `stock_metric` | `supply_demand_index` |
| 개인 매수량 | `stock_metric` | `individual_buy_volume` |
| 개인 매도량 | `stock_metric` | `individual_sell_volume` |
| 서비스·모델 설명 | `service_knowledge` | 없음 |

댓글 신호 의미처럼 서비스 설명에 해당하는 질문도 `service_knowledge`를 사용한다. 화면은
서버 허용 action·metric 외의 문자열을 만들지 않는다.

### 9.2 문맥과 화면 위치

- 상세 화면에서 챗봇을 열면 현재 종목과 선택 이력의 `stock_code`, `model_date`를 기본값으로
  사용할 수 있다.
- 목록이나 공통 화면에서 열면 사용자가 종목과 기준일을 먼저 선택하게 한다.
- `service_knowledge`는 종목·날짜를 강제하지 않는다.
- 종목·날짜를 자연어에서 추출하거나 `오늘`, `어제`를 프론트가 임의 날짜로 바꾸지 않는다.
- 과거 대화처럼 보이는 UI를 만들더라도 현재 서버가 장기 기억이나 영구 대화 저장을
  제공한다고 표현하지 않는다.

챗봇을 상세 화면에 넣을지 공통 패널·모달로 둘지는 조정할 수 있다. 새 `chat.js`·`chat.css`
등을 만들 수 있지만 기존 공통 파일을 통째로 재작성하지 않고 역할을 명확히 나눈다.

### 9.3 응답 표시

- `answer`는 사용자 문자열과 동일하게 안전한 텍스트로 삽입한다.
- `route`와 `status`는 개발자 코드 그대로만 보여주지 말고 이해 가능한 문구로 변환한다.
- `as_of`와 출처의 `model_date`가 있으면 답변 기준일로 표시한다.
- `mysql_metric`, `llm_report`, `service_document` 출처를 구분하되 내부 구현 정보는 숨긴다.
- `warnings`가 여러 개면 모두 표시한다.
- `restricted` 답변은 일반 오류가 아니며 서버가 제공한 제한 안내와 warning을 보여준다.
- `needs_clarification`은 필요한 선택 항목에 포커스를 이동하거나 안내한다.
- `not_ready`, `not_found`, `unavailable`, `failed`를 같은 `오류` 문구로 합치지 않는다.
- HTTP 400은 입력 선택을 수정할 수 있게 하고, 503·500은 재시도 가능한 서비스 오류로
  구분한다.
- 서버 응답이 아닌 임시 LLM 답변이나 임의 출처를 만들어 표시하지 않는다.

### 9.4 서비스 지식 RAG 환경 경계

서비스 문서 RAG와 Chroma 인덱스는 챗봇 담당자의 실행 환경에 준비된 백엔드 자산이다.
프론트는 이를 다시 구축하거나 로컬 Chroma 경로를 알 필요가 없다. 통합 환경에서
`service_knowledge`가 `unavailable`을 반환하면 임의 설명으로 대체하지 않고 현재 사용할 수
없음을 표시하고 백엔드 실행 환경을 확인하도록 보고한다.

## 12. 완료 기준과 제출 결과물

### 12.1 기능 완료 기준

- 최신 `develop`에서 만든 기능 브랜치다.
- 기존 검색·최근 조회·목록·상세·재시도 기능이 유지된다.
- camelCase와 과거 LLM 필드 의존이 제거된다.
- 목록·상세·보고서가 Flask가 선택한 같은 날짜별 최신 스냅샷을 표시한다.
- `invalid_request`, `not_found`, `inference_pending`, `report_pending`, `no_direction`,
  `unknown`, `insufficient_features`, `ready`, `insufficient_evidence`,
  `internal_error`를 의미에 맞게 구분한다.
- estimated·confirmed와 보고서 갱신 대기를 구분한다.
- 실제 방향 일치·불일치 같은 오해 가능한 표현이 제거된다.
- 내부 artifact ID가 일반 화면에 노출되지 않는다.
- v13 해설·결론·신호·주의 문구를 표시한다.
- 단일 댓글 결과를 일별 신호와 혼동하지 않게 표시한다.
- 챗봇이 허용 action·metric과 선택한 종목·기준일을 정확히 전송한다.
- 챗봇의 `ready`, `needs_clarification`, `not_ready`, `not_found`, `unavailable`, `failed`를
  의미에 맞게 표시한다.
- 챗봇 답변과 공개 출처·기준일·warning을 함께 표시한다.
- 투자 추천·비밀정보 요청의 `restricted` 응답을 정상 제한 안내로 표시한다.
- 챗봇 내부 경로·검색 점수·비밀정보와 임의 생성 데이터를 표시하지 않는다.
- 모바일·PC에서 핵심 정보와 오류 상태를 읽을 수 있다.

### 12.2 결과 대조 자료

담당자는 완료 보고에 다음 내용을 남긴다.

- 변경 파일과 각 파일의 역할
- 목록·상세·v13 보고서·단일 댓글·챗봇 화면 캡처
- 실제 확인한 정상·대기·근거 부족·오류 상태
- 챗봇의 분석·정확 수치·서비스 지식·제한 요청과 확인한 응답 상태
- 기존 검색·최근 조회·정렬·이력 기능 유지 여부
- 사용한 API 경로와 최종 응답 필드
- 수행한 JavaScript 검사·테스트·브라우저 환경
- 현재 데이터에서 재현하지 못한 상태와 사유

재현하지 못한 상태를 정상 동작으로 확인했다고 작성하지 않는다. 실제 DB에 특정 상태가
없으면 미검증으로 보고하고, 프론트 전용 임시 데이터가 실제 API 응답처럼 남지 않게 한다.

## 13. 현재 검증 상태

PR #10·#12가 병합된 `develop@d178211`에서 다음 백엔드 검증을 확인했다.

- 전체 비DB 테스트 381개 통과, 실제 RAG E2E 4개는 실행 환경 조건으로 제외
- 실제 DB 읽기 전용 목록 10종목 HTTP 200
- 종목 상세 HTTP 200
- 저장된 v13 보고서 HTTP 200
- 챗봇 `stock_metric`, `stock_analysis`, `restricted` 실제 응답 HTTP 200·`ready`
- 단일 댓글 실제 두 방향 모델 응답 HTTP 200
- 현재 선택된 보고서 LLM 출력 모드 `json_object` capability 확인

서비스 지식 RAG 인덱스는 챗봇 담당자 로컬 환경에 존재한다. 이 점은 현재 프론트 작업
환경에서 실제 RAG 응답까지 검증했다는 뜻은 아니다. 프론트 반영 후 실제 통합 환경과
브라우저에서 목록·상세·보고서·단일 댓글·챗봇과 각 상태를 확인해야 한다. 위 백엔드 검증을
브라우저 화면 검증 완료로 표현하지 않는다.

다음은 데이터 계약을 바꾸지 않는 범위에서 조정할 수 있다.

- 최종 레이아웃과 색상·간격
- 목록과 상세에서 강조할 정보의 우선순위
- 품질·수급 상태 배지의 위치와 문구
- 모델 근거 영역을 펼침 영역이나 모달 중 어디에 둘지
- 단일 댓글 체험 화면의 위치와 예시 문구
- 챗봇을 상세 화면, 공통 패널 또는 모달 중 어디에 둘지
- 챗봇 질문 선택 UI를 버튼·셀렉트·카드 중 어떤 형태로 표현할지
- 프론트 작업 브랜치 이름
