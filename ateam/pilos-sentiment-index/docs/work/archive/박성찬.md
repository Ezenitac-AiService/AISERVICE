## 1. 작업 목표

댓글 수집 실행기를 향후 최상위 자동화 실행기가 Python 함수로 안전하게
호출할 수 있도록 마무리한다. CLI 명령을 다시 실행하는 방식이 아니라 실행함수의
반환 결과를 통해 다음 전처리 단계의 진행 여부를 판단할 수 있어야 한다.

기존 파일 단위 완료 처리 때문에 append된 신규 댓글이 누락됐던 문제는 다음 계약을
유지해 해결한다.

- 실행할 때마다 새 파일을 만들지 않는다.
- 종목·댓글 작성일별 `from_*.jsonl` 파일에 신규 댓글을 append한다.
- 전처리는 파일 전체 완료 여부가 아니라 `raw_line_number` 워터마크 이후의 새 행을 처리한다.
- 원본 파일은 append-only로 유지한다.

상세 기능 계약은 [`specs/comment-crawling.md`](../../../specs/comment-crawling.md)와
[`specs/comment-preprocessing.md`](../../../specs/comment-preprocessing.md)를 우선한다.

## 2. 현재 확인된 구현

- 과거 이력 수집용 `crawl_until_date()`가 있다.
- 최신 증분 수집용 `crawl_from_now()`가 있다.
- `run_incremental(target)`은 `sk`, `others`를 구분해 호출할 수 있다.
- 증분 실행 결과는 `IncrementalRunSummary`로 반환한다.
- 종목별 커서, 실행 상태와 날짜별 건수는 manifest에 저장한다.
- 정상 종료한 증분 실행만 최신 경계를 갱신한다.
- 토스 API 요청 재시도, 429 대기, 커서 정지 방어와 파일 중복 방지가 구현되어 있다.
- 개인정보 식별자는 JSONL 저장 전에 해시로 비식별화한다.
- 원본 파일의 마지막 적재 줄 이후를 처리하는 `raw_line_number` 워터마크가 구현돼 있다.
- 배치 전처리와 오늘 날짜 전처리는 공통 변환 함수와 `PreprocessRunSummary`를 사용한다.
- 원본 JSONL 제너레이터, 표준 댓글 변환과 텍스트 전처리 규칙은 재사용되고 있다.

위 항목은 코드 존재 기준이다. 현재 로컬에서는 실제 토스 API·DB 연결 실행을
재검증하지 않았다.

## 3. 필수 마무리 작업

### 3.1 실행함수 계약 확정

최상위 실행기는 다음 두 호출을 순차적으로 사용할 예정이다.

```python
sk_result = run_incremental(target="sk")
others_result = run_incremental(target="others")
```

다음을 지킨다.

- CLI 인자 파싱은 `main()` 또는 CLI 경계에서만 수행한다.
- `run_incremental()` 내부에서 `sys.exit()`하지 않는다.
- 프로그램 호출자는 대상 수, 성공·실패 수, 신규 댓글 수와 실패 사유를 확인할 수 있다.
- 종목별 페이지 수, 실행시간, 종료 사유를 최상위 실행기가 관측할 수 있게 반환 구조를 보완한다.
- 일부 종목 실패 후에도 나머지 종목 수집은 계속하고 최종 결과에서 부분 실패를 구분한다.

### 3.2 DB 초기화 실패 계약 수정

현재 `build_connection()`이 실패하면 `None`을 반환하지만 실행기가 곧바로
`db_connecter.select_stock()`을 호출한다. 따라서 주석과 달리 DB 없이 JSONL만
수집하는 동작은 성립하지 않는다.

다음 중 실제 요구에 맞는 하나의 계약으로 정리하고 코드·문서를 일치시킨다.

1. 종목 조회에 DB가 필수라면 실행 시작 단계에서 명시적인 초기화 실패로 반환한다.
2. DB 없이 수집해야 한다면 `stock_id`, 종목명과 `subjectId`를 외부에서 전달받는
   별도 실행 계약을 정의한다.

`None.select_stock()`과 같은 우발적인 `AttributeError`로 실패하게 두지 않는다.

### 3.3 계층 책임 정리

목표 의존 방향은 다음과 같다.

```text
jobs → collection
jobs → storage
```

- `collection`은 외부 API 요청과 외부 응답 반환을 담당한다.
- `storage`는 JSONL, manifest와 DB 입출력을 담당한다.
- `jobs`는 수집과 저장 순서를 조합한다.
- 크롤러에 전달되지만 실제로 사용되지 않는 `db_connecter` 인자를 정리한다.
- 크롤러가 JSONL 저장 직후 전처리 결과를 DB에 적재한다는 오래된 docstring을 수정한다.

챗봇 기능 병합 전에는 대규모 폴더 이동을 수행하지 않는다. 이번 작업에서는 함수 책임과
호출 계약을 우선 정리하고, 실제 파일 이동은 통합 이후 별도 구조 개편 작업에서 진행한다.

### 3.4 비식별화 계약 정리

현재 저장물은 외부 응답을 그대로 보존한 원본이 아니라 개인정보를 해시한
`비식별화 원본`이다.

- 코드와 문서에서 저장 데이터의 성격을 `비식별화 원본`으로 일치시킨다.
- `SECRET_SALT`, `SECRET_SALT2`의 환경변수 이름과 필수 여부를 `.env.example`에 기록한다.
- 비밀값 자체는 코드, 문서와 로그에 기록하지 않는다.
- 솔트가 없으면 댓글 처리 중 `TypeError`가 발생하기 전에 실행 시작 단계에서 명확히 실패시킨다.
- 닉네임이나 프로필 ID가 없는 댓글 전체를 제외하는 정책이 필요한지 확인한다.

### 3.5 증분 커서 정책 보존

- 자동화 주기가 10분이어도 요청 페이지 수를 임의로 고정하지 않는다.
- 이전 정상 수집 경계에 도달할 때까지 신규 댓글을 수집한다.
- API 실패나 커서 정지 시 최신 경계를 앞당기지 않는다.
- 자동화 시작을 이유로 manifest 커서를 삭제하지 않는다.
- 장기 미수집분을 따라잡는 초기 동기화와 정상 주기 운영을 구분한다.
- 이전 실행이 끝나지 않았을 때 다음 실행과 겹치지 않도록 최상위 실행기에 필요한 상태를 제공한다.

### 3.6 실행 관측 정보 제공

최상위 실행기와 운영 로그에서 최소한 다음 값을 확인할 수 있어야 한다.

| 항목 | 목적 |
|---|---|
| 대상·성공·실패 종목 수 | 부분 실패 판단 |
| 종목별 신규 댓글 수 | 수집량 확인 |
| 종목별 요청 페이지 수 | API 사용량 추정 |
| 종목별·전체 실행시간 | 10분 주기 가능성 측정 |
| 종료 사유 | 정상 종료와 중단 구분 |
| 실패 종목과 사유 | 재실행 대상 판단 |
| 마지막 정상 경계 | 증분 재개 상태 확인 |

### 3.7 증분 전처리 실행경계 마무리

핵심 요구사항인 append 원본의 행 단위 증분 전처리는 구현돼 있다. 발표 전에는
DDL을 변경하지 않고 기존 실행기와의 연결을 다음 범위로 마무리한다.

- `jobs/preprocess_comments.py`와 `jobs/today_preprocess_comments.py` 중 최상위
  실행기가 호출할 공식 실행함수를 하나의 명확한 계약으로 정한다.
- 수집 실행이 실제로 기록한 파일 목록을 반환하고, 전처리 실행함수가 해당 파일을
  직접 입력받도록 연결한다.
- 장기 미수집분이나 지연 댓글이 과거 작성일 파일에 append됐을 때 오늘 날짜 필터에서
  누락되지 않게 한다.
- 날짜로 전처리 대상을 다시 찾는 실행기는 필요하면 얇은 수동·CLI 래퍼로만 유지한다.
- `collection/comment_preprocessing.py`의 로직은 외부 수집이 아니라
  `storage → analysis → storage`를 조합하므로 최종 책임을 `jobs`로 정리한다.
- 챗봇 병합 전에는 파일을 대규모로 이동하지 않고, 우선 공식 호출자와 함수 책임을
  명확히 한다.

### 3.8 전처리 반환·실패 계약 통일

- 최상위 실행기는 `PreprocessRunSummary.total`, `inserted`, `failed`,
  `failed_files`를 확인할 수 있어야 한다.
- `incremental_and_preprocess.py`가 전처리 요약을 적재 건수처럼 출력하는 부분을 수정한다.
- 수집 성공 여부뿐 아니라 전처리 부분 실패도 최종 실행 결과에 반영한다.
- 실행함수끼리 연결할 때 CLI용 `main()`이나 `sys.exit()`를 호출하지 않는다.
- 전처리 실패 후 다음 단계인 토큰화를 진행할지 최상위 실행기가 판단할 수 있게 한다.

### 3.9 현재 DB 적재 계약 확인

현재 `preprocess_db.py`는 `INSERT IGNORE`를 사용하지만 저장소의 `schema.sql` 설명과
다른 적재 코드에는 `ON DUPLICATE KEY UPDATE`가 남아 있다. 실제 운영 DB 스키마도
현재 로컬에서 확인할 수 없다.

발표 전에는 DDL을 임의로 변경하지 않고 다음 내용을 확인해 보고한다.

- 실제 `preprocessed_comment` 테이블의 키와 컬럼
- 같은 `comment_id`가 다시 들어왔을 때 기존 행을 유지할지 최신 수정본으로 갱신할지
- `stock_id`, `raw_line_number`, `source_comment_file_id`가 실제 스키마에 존재하는지
- 저장소 `schema.sql`이 현재 정본인지 더 이상 사용하지 않는 파일인지

확인 결과 데이터 계약과 적재 동작이 다르면 임의로 선택하지 않고 팀장에게 보고한다.

### 3.10 기존 전처리 로직 보존

다음 구현은 이번 마무리 작업에서 다시 작성하지 않는다.

- `iter_jsonl_records()` 제너레이터 기반 원본 순회
- 외부 중첩 레코드의 표준 댓글 컬럼 변환
- 종목코드·식별자·시각 정규화
- 제목·본문 결합, 이모지 제거와 소셜 표현 정규화
- 단일 댓글 추론과 공유하는 `preprocess_comment_text()`

제너레이터는 워터마크 이전 줄의 JSON 파싱을 생략하고 신규 레코드를 순차 제공하는
현재 목적에 맞게 사용되고 있다. Pandas DataFrame 생성 시 신규 레코드를 메모리에
모으는 것은 현재 일괄 전처리 계약에서 허용한다.

## 4. 검증 요구사항

이 프로젝트의 기존 테스트 파일은 기능 구현을 요청받은 에이전트가 생성한 것으로,
별도의 테스트 파일 체계를 만드는 것을 팀원 마무리 작업의 목표로 삼지 않는다.
다만 변경한 실행 계약은 가능한 범위에서 다음 동작을 확인하고 결과를 보고한다.

- `sk`, `others`가 각 실행함수 호출에서 올바르게 분리된다.
- DB 초기화 실패가 정의된 실패 결과로 처리된다.
- 정상 종료에서만 증분 경계가 갱신된다.
- 실패 후 재실행해도 누락 없이 이전 경계부터 다시 수집한다.
- 같은 댓글을 다시 받아도 JSONL에 중복 누적되지 않는다.
- 같은 날짜 파일에 append된 신규 행이 전처리 대상으로 선택된다.
- 수집이 반환한 과거 작성일 파일도 전처리 대상으로 전달된다.
- 솔트 누락 시 실행 시작 단계에서 이해 가능한 오류가 발생한다.
- 일부 종목 실패가 전체 결과에 부분 실패로 나타난다.
- 전처리 부분 실패가 최상위 호출자에게 반환된다.

실제 토스 API·DB 연동, 장기 미수집분 동기화와 10분 주기 실행시간은 별도의
운영 환경 검증으로 남기고 완료한 것처럼 표시하지 않는다.

## 5. 발표 이후 개선 과제

다음 항목은 안정적인 최종 구조에 필요하지만 DB 변경과 운영 데이터 확인이 필요하므로
발표 전 마무리 범위에서 제외한다.

- `last_scanned_line`과 처리 상태를 원본 파일별로 저장하는 컬럼 또는 별도 테이블
- 유효 댓글의 마지막 적재 줄과 실제로 검사한 마지막 원본 줄의 분리
- 손상된 JSONL 한 줄을 기록·격리하고 이후 정상 줄을 처리하는 정책
- 댓글 수정본을 반영하기 위한 UPSERT 계약
- 큰 원본 파일을 매번 처음부터 순회하지 않기 위한 byte offset 검토
- 실제 운영 DB 기준 DDL과 저장소 스키마 파일의 정본화

이 작업은 실제 DB 스키마 확인, 기존 데이터의 초기 상태 이관과 트랜잭션 설계를
동반하므로 별도 개선 작업으로 진행한다.
