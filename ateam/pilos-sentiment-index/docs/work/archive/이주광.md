## 1. 현재 확정한 방향

### 댓글 불변 처리

- 현재 MVP에서는 같은 `comment_id`의 댓글을 불변 데이터로 취급한다.
- 대량 초기 적재에서 파일 간 중복 댓글 하나가 전체 트랜잭션을 롤백하지 않도록
  `INSERT IGNORE`를 유지한다.
- 댓글 수정 시 기존 ID가 유지되는지 새 ID가 생성되는지는 확인하지 못했다.
- 최신 수정본 UPSERT, 재토큰화와 일별 문서 재생성은 현재 범위에 넣지 않는다.

### 토크나이저 버전 수동 관리

- `TOKENIZER_VERSION = "kiwi_ver1"`은 사람이 명시적으로 관리한다.
- 설정만 바뀌고 버전이 유지되는 자동 변경을 허용하지 않는다.
- 품사, 포함 표현, 불용어와 사용자 사전 변경은 모델 입력 계약 변경으로 본다.
- 계약 변경 시 새 토크나이저 버전, 일별 문서 재생성과 모델 재학습 범위를 함께 결정한다.
- 자동 버전 생성은 현재 필수 개선사항으로 두지 않는다.

수동 관리의 목적은 토큰 설정 변경이 이후 벡터화·학습·추론에 조용히 전파되는 것을
막고, 사람이 영향 범위를 확인한 뒤 새 버전을 승인하도록 하는 것이다.

### DB 토큰 컬럼명

현재 코드는 물리 DB 컬럼 `tokenized_comment.tokens`를 사용하고 Python 경계에서
`kiwi_tokens`로 변환한다. `DATA_CONTRACT.md`에는 물리 컬럼이 `kiwi_tokens`로
기록돼 있어 불일치가 있지만, 저장소 DB 스키마가 최신이 아니므로 현재 수정하지 않는다.
실제 DB 스키마 최신화 작업에서 물리 컬럼과 논리 필드 명칭을 확정한다.

### 일별 문서 스냅샷

- 일별 문서는 같은 종목·날짜의 최신 행을 UPSERT하지 않고 새 스냅샷으로 저장한다.
- 신규 댓글이 추가되면 그 시점까지의 장 마감 전 댓글 전체로 새 문서를 만든다.
- 과거 스냅샷과 댓글 매핑을 보존해 댓글 여론이 시간에 따라 달라지는 과정을 확인한다.
- 10분 자동화에서 같은 날짜의 스냅샷과 매핑 데이터가 증가하는 저장비용은 현재
  서비스 목적을 위해 감수한다.
- 후속 추론과 화면은 같은 종목·날짜의 최신 `daily_document_id`를 현재 상태로 사용한다.

DB를 사용한 이유는 최신 결과 한 건만 보관하기 위해서가 아니라, 실시간으로 수집되는
댓글 구성의 변화와 그 시점의 분석 결과를 연결해 서비스하기 위해서다.

### 텍스트 처리 계약 버전

별도 일별 문서 규칙 버전 컬럼을 추가하지 않는다. 현재 `TOKENIZER_VERSION`은
형태소 분석기 이름만이 아니라 모델 입력을 만드는 텍스트 처리 계약의 버전으로 관리한다.

다음 변경은 기존 `kiwi_ver1` 결과를 조용히 수정하지 않고 새 버전과 재생성·재학습
범위를 함께 결정한다.

- 품사·포함 표현·불용어와 사용자 사전
- 토큰 `form`의 TF-IDF 문자열 변환
- 일별 문서 댓글 포함 범위와 정렬·집계 규칙
- 모델 입력 문서의 의미를 바꾸는 기타 처리 규칙

현재 서비스 v4의 규칙은 동결한다. 버전을 올릴 때는 기존 결과를 UPDATE하지 않고 새
토큰·일별 문서·모델 계보를 생성한다.

### 수집 계층 신뢰 범위

- 현재 MVP에서는 이미 처리한 과거 날짜에 새 댓글이 뒤늦게 추가되지 않는다는 수집
  계약을 신뢰한다.
- 과거 날짜의 댓글 구성이 바뀌는 경우까지 모든 하위 단계가 자동 재처리하도록 만들지
  않는다.
- 실제로 과거 댓글이 추가되는 데이터가 확인되면 일별 문서 재생성 범위와 모델 Dataset
  계보를 다시 검토한다.

모든 가능성을 방어하기보다 오류 영향이 크고 검사 비용이 낮은 버전·아티팩트 일치
조건을 우선 검증한다. 발생 여부가 확인되지 않았고 대응 비용이 큰 과거 데이터 변경은
현재 계약으로 제한하고 개선 후보로 남긴다.

## 2. 현재 토큰화 구현

```text
Kiwi와 사용자 사전 생성
→ kiwi_ver1 결과가 없는 전처리 댓글 2,000건 조회
→ text 일괄 형태소 분석
→ 품사·포함 표현·불용어 기준으로 토큰 선택
→ 500건 단위로 tokenized_comment 적재
→ 조회 배치 적재 수 일치 확인
→ 마지막 preprocessed_comment_id 이후 반복
```

책임 배치는 다음과 같다.

- `jobs/tokenize_comments.py`: 조회·토큰화·저장 순서와 실패 전파
- `analysis/tokenizer.py`: Kiwi 형태소 분석과 토큰 선택
- `analysis/tokenizer_settings.py`: `kiwi_ver1` 설정
- `storage/tokenize_db.py`: 미토큰화 조회와 결과 적재

배치 토큰화 구조와 재실행 경계는 현재 자동화 실행함수로 사용 가능한 상태다.

## 3. 필수 수정: 단일 댓글 토큰 계약

### 확인된 문제

배치 토큰화는 다음 설정을 모두 전달한다.

```text
POS_TAGS
INCLUDE_FORMS
STOPWORDS
USER_DICTIONARY
```

단일 댓글 추론은 `USER_DICTIONARY`가 적용된 Kiwi 객체는 사용하지만
`tokenize_comment()` 호출에 `POS_TAGS`, `INCLUDE_FORMS`, `STOPWORDS`를
전달하지 않는다.

따라서 현재 단일 댓글은 학습 일별 문서와 다른 규칙으로 토큰을 선택할 수 있다.
특히 품사 필터, 불용어와 원문의 `-잖-`이 `않/VX`으로 분석되는 예외 교정이
빠진다.

### 수정 목표

- 단일 댓글과 배치 댓글이 같은 `kiwi_ver1` 토큰 선택 설정을 사용한다.
- 설정 전달을 호출자마다 반복하지 않도록 현재 버전 설정을 적용하는 공통 호출
  경계를 검토한다.
- 단일 댓글 서비스가 임의 설정을 조합하지 않고 학습 모델의 토큰 계약을 사용한다.
- 입력 댓글 하나를 배치 함수와 단일 함수로 각각 처리했을 때 선택 토큰의
  `form`과 `tag`가 같음을 확인한다.
- 수정 후 단일 댓글 TF-IDF 입력이 기존 모델 vocabulary와 같은 규칙으로 생성되는지 확인한다.

이 수정은 발표용 단일 댓글 체험 서비스 전에 반드시 완료한다.

## 4. 최상위 실행기 구현 시 고려사항

### 실행 방식

- CLI 명령을 subprocess로 다시 실행하지 않고 각 기능의 Python 실행함수를 호출한다.
- 각 단계의 반환값과 예외를 확인한 뒤 다음 단계 진행 여부를 결정한다.
- 최상위 Python 실행기는 Windows 배치 파일이 시작하고, 작업 스케줄러는 해당 배치
  파일을 정해진 주기로 호출한다.
- 이전 자동화 실행이 끝나지 않았으면 새 실행을 겹쳐 시작하지 않는다.

### 댓글 수집부터 Chroma 적재까지의 잠정 순서

```text
run_incremental("sk")
→ run_incremental("others")
→ 두 수집 결과와 실제 기록 파일 확인
→ 해당 파일의 신규 줄 전처리
→ PreprocessRunSummary 확인
→ run_pending_comment_tokenization()
→ 토큰화 적재 건수 또는 예외 확인
→ run_daily_document_building()
→ 성공·실패 대상 수 확인
→ run_supply_demand_collection()
→ 활성 Positive·Negative DB 아티팩트와 bundle 로드
→ 모델·토큰 버전 호환성 검증
→ 현재 DB 기준 미완료 추론 대상 조회
→ 대상이 없으면 정상 완료
→ 두 방향 모델 추론과 품질 상태 저장
→ 현재 모델 버전의 calibration artifact 로드
→ calibration과 두 DB artifact 전체 identity 검증
→ 수급 상태와 활성 모델 방향 결정
→ LLM 보고서 생성 또는 최신 상태 갱신
→ 임준화 담당 Chroma 적재 실행함수 호출
→ Chroma 실행 결과의 성공·기존·제외·실패 수 확인
```

- 수집 일부 실패 시 이미 수집한 댓글의 전처리를 허용할지는 정책으로 명시한다.
- 전처리 파일 실패가 있으면 토큰화를 진행할지 중단할지 명시한다.
- 토큰화는 오류를 예외로 전달하므로 실패 시 일별 문서 생성을 시작하지 않는다.
- 일별 문서 실패 수가 0보다 크면 후속 추론을 시작하지 않는다.
- 신규 토큰이 있는 종목·날짜만 스냅샷 대상으로 선택하고, 대상이 없으면 정상 완료한다.
- 자동 운영 흐름에 모델 재학습을 포함하지 않는다.
- 활성 모델 누락이나 bundle 손상을 추론 대상 없음으로 숨기지 않도록 모델 로드와
  호환성 검증을 미추론 대상 조회보다 먼저 수행한다.
- 이번 실행에서 생성한 일별 문서 수만으로 추론 여부를 결정하지 않는다. 이전에
  생성됐지만 수급 데이터가 뒤늦게 도착한 문서도 현재 DB 상태에서 다시 찾는다.
- LLM 일부 대상 실패만으로 이미 생성된 정상 보고서의 Chroma 적재까지 막지 않는다.
- 최상위 실행기는 Chroma 내부 저장 방식을 결정하지 않고 담당자가 제공하는 실행함수와
  반환 요약만 사용한다. 세부 적재·검색 계약은 `docs/work/임준화.md`에서 관리한다.

### 토크나이저 계약 확인

- 최상위 실행 시작 시 현재 `TOKENIZER_VERSION`을 로그와 실행 결과에 남긴다.
- 일별 문서, 등록 모델과 추론이 요구하는 `tokenizer_version`이 현재 버전과
  다르면 조용히 진행하지 않고 중단한다.
- 품사·불용어·사용자 사전 변경은 버전 변경과 재학습 결정 없이 자동 반영하지 않는다.
- 향후 필요하면 설정 내용의 fingerprint를 기록해 수동 버전 누락을 검출할 수 있지만,
  현재 발표 전 필수 구현에는 포함하지 않는다.

`fingerprint`는 설정 내용을 일정한 순서로 직렬화해 만든 식별값이다. 버전을 자동으로
결정하기보다, 사람이 지정한 버전과 실제 설정 내용이 달라졌는지 검사하는 안전장치로
사용할 수 있다.

### LLM 실패와 Chroma 후속 단계

LLM 보고서 뒤에 챗봇 RAG용 Chroma 적재가 이어질 가능성이 높으므로 LLM을 자동화의
마지막 단계로 보지 않는다. 다만 일부 종목의 보고서 생성 실패가 다른 정상 보고서의
색인까지 막게 하지는 않는다.

```text
LLM 응답 계약 검증 2회 실패
→ 검증된 정형 근거로 deterministic fallback 보고서 저장
→ commentary_source로 fallback 사실을 생산 계약에 표시
→ Chroma 실행함수 호출 가능

LLM 통신·HTTP 일시 실패
→ 해당 보고서는 재시도 대상으로 유지
→ 다른 정상·기존 보고서는 Chroma 적재 계속

calibration·모델 identity·DB 계약 실패
→ 새 보고서를 정상 결과로 만들지 않음
→ 실패 상태를 반환하고 비호환 신규 결과를 후속 단계에 전달하지 않음
```

Chroma 문서 ID, UPSERT, metadata, estimated·confirmed 교체와 검색 필터는 임준화 담당
영역이다. 이주광 담당 범위에서는 LLM 보고서의 생산 상태를 명확히 반환하고, 최상위
실행기가 Chroma 실행 결과를 기록·판정하는 경계까지만 구현한다.

## 5. 모델 설정과 실행 경계 마무리

현재 핵심 기능은 구현돼 있지만 서비스 모델을 식별하는 같은 값이 여러 위치에 있거나
실행기가 다른 실행기의 상수를 가져오는 구조가 남아 있다.

### 현재 확인된 중복과 의존

- `jobs/train_model.py`가 모델명, 방향, 모델 버전과 출력 경로를 관리한다.
- `jobs/predict_model.py`와 `jobs/analyze_single_comment.py`는 학습 실행기의
  `MODEL_TRAINING_CONFIGS`를 가져온다.
- `service/single_comment_service.py`는 모델명, 버전과 방향을 다시 선언한다.
- `jobs/generate_llm_reports.py`는 모델명, 모델 버전과 아티팩트 스키마 버전을
  다시 선언한다.

학습한 모델로 추론한다는 설계 의도는 맞다. 문제는 추론 실행기가 학습 실행기 모듈에
의존하고 같은 서비스 식별값이 여러 파일에서 각각 변경될 수 있다는 점이다.

### 공통 설정 분리

학습·추론·단일 댓글·calibration·LLM 보고서가 함께 사용하는 다음 값은 중립적인 모델
설정 모듈 한 곳에서 관리한다.

```text
서비스 모델명
현재 활성 서비스 모델 버전
Positive·Negative 모델 방향
요구 토크나이저 버전
모델 bundle 스키마 버전
calibration 스키마와 artifact 경로
최소 recognized feature 수
최소 vocabulary coverage
```

- `train_model`과 `predict_model`이 서로를 import하지 않고 같은 설정 모듈을 사용한다.
- Ridge `alpha`, TF-IDF `min_df`·`max_df`처럼 학습에만 필요한 하이퍼파라미터는
  학습 설정에 둔다.
- 앞으로 새 모델을 먼저 학습하고 검증한 뒤 서비스에 전환할 수 있도록 `학습 대상
  모델 버전`과 `현재 활성 서비스 모델 버전`을 같은 개념으로 고정하지 않는다.
- 설정 파일은 코드의 중복을 막고, 실제 DB 행과 bundle의 일치는 별도 실행 검증으로
  확인한다.

### DTO와 실행 검증의 역할

- DTO는 버전 필드의 자료형, 필수 여부와 허용값 같은 전달 계약을 검증한다.
- DTO가 현재 활성 버전과의 일치까지 강제하지 않는다. 그렇게 하면 과거 버전 데이터를
  조회하거나 표시하는 것까지 막을 수 있다.
- 현재 실행에 함께 사용할 수 있는지는 DB·파일 경계를 지난 뒤 호환성 검증 함수가
  판단한다.
- 최상위 실행기는 각 실행함수의 결과에서 실제 처리 버전과 아티팩트 ID를 받아 다음
  단계 진행 여부를 결정한다.

직접 Python 함수를 호출하는 최상위 실행기에서는 작은 `dataclass`나 명시적인 dict
반환 계약을 사용할 수 있다. 프로세스 밖으로 직렬화해 전달해야 할 때만 DTO 적용을
확대한다.

### 필수 호환성 조건

다음 값이 일치하지 않으면 추론이나 보고서 생성을 시작하지 않는다.

```text
현재 TOKENIZER_VERSION
= daily_document.tokenizer_version
= Positive bundle.tokenizer_version
= Negative bundle.tokenizer_version

현재 활성 모델 식별값
= DB artifacts의 모델명·방향·버전·스키마
= 로컬 bundle의 모델명·방향·버전·스키마
= calibration이 요구하는 모델 식별값
```

현재 등록 모델 로더는 DB 아티팩트 행과 로컬 bundle을 비교한다. 그러나 일별 추론은
현재 코드의 `TOKENIZER_VERSION`으로 문서를 조회한 뒤 고정 모델 v4를 불러오므로,
현재 토큰 버전과 bundle 토큰 버전의 직접 비교를 추가해야 한다. 이 검증은 최상위
실행기에만 의존하지 않고 독립 실행되는 추론·단일 댓글 경계에서도 수행한다.

Positive와 Negative의 모델 버전·토큰 버전도 서로 같아야 한다. 버전 불일치는 대상
없음과 달리 정상 상태가 아니므로 명확한 오류로 중단한다.

## 6. 모델 추론 서비스화 결정

모델 학습·벡터화·Ridge 추론 계산은 유지한다. 이번 마무리 작업은 반복 자동화에서
대상을 정확히 찾고, 추론 품질과 수급 상태를 DB·Flask·LLM까지 같은 의미로 전달하는
서비스 운영 계약을 구현하는 범위다.

| 범위 | 현재 상태 |
|---|---|
| Positive·Negative v4 학습·bundle 저장 | 구현 완료 |
| 최신 일별 문서 두 방향 추론·결과 적재 | 구현 완료 |
| 공통 모델 설정 통합 | 결정됨·구현 필요 |
| 현재 토큰 버전과 두 bundle 호환성 검증 | 부분 구현·보강 필요 |
| 대상 0건 정상 종료 | 결정됨·구현 필요 |
| 활성 artifact 기준 미완료 대상 조회 | 결정됨·구현 필요 |
| 품질 상태 DB 저장과 Flask·LLM 전달 | 결정됨·DDL 및 구현 필요 |
| estimated·confirmed 표시와 보고서 갱신 | 결정됨·DDL 및 구현 필요 |

### 현재 유지할 학습·추론 구조

- 모델 학습은 `confirmed` 수급만 사용하며 자동 운영에 포함하지 않는다.
- Positive는 양수 수급일, Negative는 음수 수급일 Dataset으로 각각 학습한다.
- 학습 시 `fit_transform`, 검증·추론 시 학습된 vectorizer의 `transform`을 사용한다.
- 같은 일별 문서를 두 방향 모델로 모두 추론해 결과를 저장한다.
- 실제 수급 부호가 서비스에서 사용할 활성 모델 방향을 결정한다.
- 실제 수급지수는 text-only Ridge의 입력 특성이 아니므로 수급 상태가 바뀌어도 같은
  문서와 bundle의 Positive·Negative 추론을 다시 계산하지 않는다.

### 대상 없음과 실행 실패 구분

추론 대상이 없는 것은 정상적인 멱등 실행 결과다.

```text
추론 대상 0건
→ 성공 0건
→ 실패 0건
→ 정상 종료
```

DB 연결 실패, 활성 모델 누락, bundle 로드 실패, 버전 불일치와 추론 계산 실패는
실제 오류로 구분한다. 현재 `run_database_inference()`는 대상이 없으면 `ValueError`를
발생시키므로 자동화 전에 정상 요약 반환으로 변경해야 한다.

### DB 현재 상태 기준 미완료 대상

이번 실행에서 생성된 `daily_document_id`를 다음 단계로 직접 넘기지 않는다. 검증된
활성 Positive·Negative `artifact_id`를 기준으로 매 실행마다 다음 대상을 조회한다.

```text
종목·날짜별 최신 daily_document
+ 같은 종목·날짜의 supply_demand 존재
+ (
    활성 Positive artifact 결과 없음
    OR 활성 Negative artifact 결과 없음
  )
→ 미완료 추론 대상
```

일별 문서와 수급의 생성 시점이 다르므로 `이번 일별 문서 생성 수가 0`이라는 이유로
추론을 생략하지 않는다. 현재 추론은 기간 내 최신 문서를 모두 다시 계산한 뒤 저장
단계에서 기존 결과를 제외하므로 기능상 멱등이지만, 자동화에서는 미완료 대상만 먼저
조회해 불필요한 반복 벡터화와 추론을 줄인다.

### 추론 품질 상태 저장

방향별 `sentiment_index_result`에 기존 `recognized_feature_count`와 함께 다음 값을
저장한다. 이 변경을 위한 DDL 수정을 허용한다.

```text
inference_status
unique_token_count
vocabulary_coverage
```

공식 판정 기준은 현재 추론기 규칙을 유지한다.

```text
recognized_feature_count < 5
OR vocabulary_coverage < 0.6
→ insufficient_features
```

`insufficient_features` 결과도 점수와 계산 근거를 DB에 저장해 재현·검수할 수 있게
한다. 서비스 품질 판정은 실제 수급 방향이 선택한 활성 모델 결과의 상태를 사용한다.
비활성 모델의 품질 상태만 부족한 경우에는 활성 결과의 정상 사용을 막지 않는다.

Flask와 LLM은 별도 임계값을 만들거나 품질을 재판정하지 않고 DB의
`inference_status`를 그대로 사용한다.

```text
ready
→ 모델 결과 사용 가능

insufficient_features
→ 계산 결과는 보존
→ 화면에 분석 근거 부족 표시
→ LLM 호출과 신뢰 가능한 모델 해석 제한
```

현재 실행기는 품질 상태와 coverage를 계산하지만 DB에 저장하지 않고, LLM 신호는
인식 특성이 0인지 여부만 확인한다. DDL·저장·조회·DTO·Flask·LLM을 함께 수정해야
단일 기준이 된다.

### 품질 컬럼 마이그레이션

기존 추론 결과가 있으므로 새 컬럼을 바로 `NOT NULL`로 추가하지 않는다.

```text
nullable 컬럼 추가
→ 기존 daily_document와 정확한 모델 bundle로 품질 값 재계산
→ 기존 결과 backfill
→ 누락·범위 확인
→ NOT NULL과 CHECK 제약 적용
```

실제 DDL과 기존 데이터 backfill은 학원 DB에서 확인하고 실행한다.

### `estimated`와 `confirmed` 서비스 정책

- `estimated`는 장중 실시간 임시 수급으로 화면과 LLM 보고서에 사용할 수 있다.
- 화면과 보고서는 반드시 `추정 수급 기반`임을 표시한다.
- `confirmed`는 장 마감 후 공식 수급이며 화면과 보고서의 확정 상태가 된다.
- 학습 Dataset은 기존대로 `confirmed`만 사용한다.
- 확정 행을 이후 장중 추정값으로 낮추지 않는다.

수급이 `estimated`에서 `confirmed`로 바뀌어도 같은 일별 문서의 두 방향 모델 추론은
재사용한다. 실제 수급 부호로 활성 결과를 다시 선택하고 LLM 보고서와 화면만 최신
상태로 갱신한다.

```text
estimated 양수 → Positive 결과 사용
confirmed 음수 → 기존 Negative 결과로 전환
→ 모델 재추론 없이 LLM 보고서 갱신
```

### LLM 보고서 최신 상태 갱신

새 `daily_document_id`에는 새 보고서 행을 INSERT한다. 같은 문서에서 더 최신 수급
관측값이 들어오거나 `estimated → confirmed`로 전환되면 기존 서비스용 보고서를
재생성해 UPDATE한다. 발표 전에는 같은 문서의 estimated·confirmed 보고서 전체 이력을
별도 보존하지 않는다.

이를 판단하기 위해 최소 다음 필드를 수급 조회부터 보고서 DTO·저장·Flask 응답까지
전달한다.

```text
supply_data_status: estimated | confirmed
supply_observed_at: datetime
```

`llm_report`에는 현재 수급 상태와 관측 시각을 저장하고, UPDATE 시각을 구분해야 하면
`updated_at`을 추가한다. 현재 LLM 대상 조회와 DTO에는 `actual_supply_index`만 있고
이 두 값은 없으므로 신규 구현이 필요하다.

보고서 입력 해시 판정은 다음으로 변경한다.

```text
같은 생성키 + 같은 input_hash
→ 기존 보고서 사용

같은 생성키 + 다른 input_hash
+ 더 최신 estimated 관측 또는 confirmed 전환
→ LLM 재생성 후 기존 보고서 UPDATE

같은 생성키 + 다른 input_hash
+ 허용된 수급 상태 변화 없음
→ 프롬프트·근거의 비정상 변경으로 오류

confirmed 보고서 + estimated 입력
→ 상태 강등 금지
```

기존 보고서는 생성 당시 수급 상태를 저장하지 않았으므로 정확한 상태 복원이 어렵다.
마이그레이션 시 현재 수급 상태 기준으로 서비스용 보고서를 재생성하거나 기존 행을
`unknown`으로 두는 방법 중 실제 DB 상태에 맞춰 결정한다. 최신 상태 하나만 서비스하는
현재 목표에는 재생성이 더 단순하다.

## 7. 댓글 수급 신호 calibration 마무리

Calibration은 Ridge raw 출력값을 같은 모델의 과거 출력 분포에 상대화해 0~100
`comment_signal_score`로 바꾸는 모델 artifact다. 감성 확률이나 미래 수급·주가
예측값이 아니며, 점수 `50`도 감성 중립이 아니라 과거 출력 분포의 중앙 수준이다.

| 범위 | 현재 상태 |
|---|---|
| 학습 범위 전체 재추론 CSV·요약 생성 | 구현 완료 |
| 방향별 0~100 백분위 calibration 생성·JSON 저장 | 구현 완료 |
| calibration 구조·단조성 로드 검증 | 구현 완료 |
| 실제 수급 방향 선택과 신호·비교 이력 계산 | 구현 완료 |
| calibration과 두 DB artifact의 전체 identity 운영 검증 | 검증 함수 구현·운영 연결 필요 |
| DB `inference_status`를 신호 품질 기준으로 사용 | 결정됨·구현 필요 |
| 수급 상태·관측 시각의 신호 DTO 전달 | 결정됨·구현 필요 |
| 대상 없음 시 LLM client 지연 생성 | 결정됨·구현 필요 |

### 생성과 운영 시점

Calibration 생성은 10분 자동화에 포함하지 않는다. 새 모델 버전을 만들 때 실제 학습
범위 문서를 Positive·Negative 모델로 모두 재추론하고, 방향별 raw 출력 분포에서
0%부터 100%까지 1단위 백분위 지점 101개를 생성한다.

```text
새 모델 버전 학습
→ 학습 범위 전체 문서를 두 방향 모델로 재추론
→ 재추론 CSV와 검수 요약 생성
→ 방향별 calibration JSON 생성
→ 모델·calibration 상호 검증
→ 활성 서비스 버전 전환
```

10분 운영 실행은 현재 활성 버전의 calibration을 로드하고 검증해 신호 계산에만
사용한다. 예시값이나 합성값으로 production calibration을 만들지 않는다.

### 방향별 점수 변환

- 실제 수급지수가 양수면 Positive 결과를 활성화하고 해당 출력의 백분위를 사용한다.
- 실제 수급지수가 음수면 Negative 결과를 활성화하고, 더 강한 음수가 높은 신호가
  되도록 `100 - percentile`을 사용한다.
- 수급지수가 0이면 방향을 임의로 고르지 않고 `no_direction`과 null 점수를 반환한다.
- 분포 최솟값 밖은 0, 최댓값 밖은 100으로 제한한다.
- 신호가 없는 날은 직전 신호와 최근 5거래일 평균 계산에서 제외한다.

### 실제 artifact identity 검증 연결

`analysis/signal_calibration.py`의 `verify_calibration_matches_artifact()`는 다음 전체
항목을 비교하도록 구현돼 있다.

```text
model_name, model_version
artifact_type, artifact_schema_version
tokenizer_version, vectorizer_name, scaler_name
dataset_start_date, dataset_end_date
방향별 정확한 artifact_id
```

그러나 현재 `generate_llm_reports.py`는 이 함수를 호출하지 않고 모델명·모델 버전·
아티팩트 스키마만 먼저 확인한다. 활성 결과의 artifact ID는 신호 계산 중 비교하지만
calibration과 두 실제 DB artifact의 전체 교차검증은 운영 시작 시 수행되지 않는다.

보고서 생성 전에 Positive·Negative DB artifact를 조회해 각각
`verify_calibration_matches_artifact()`를 실행한다. 두 방향 중 하나라도 불일치하면
대상별 처리로 넘어가지 않고 전체 실행을 중단한다.

### 추론 품질 상태 재사용

현재 신호 계산은 `recognized_feature_count == 0`일 때만
`insufficient_features`로 판단한다. 모델 추론 서비스화 이후에는 이 재판정을 제거하고
활성 `sentiment_index_result.inference_status`를 그대로 사용한다.

```text
활성 결과 ready
→ calibration 적용과 0~100 신호 계산

활성 결과 insufficient_features
→ raw 추론 결과는 DB에 보존
→ comment_signal_score와 signal_level은 null
→ 비교 이력에서 제외
→ LLM 호출과 정상 분석 표현 제한
```

비활성 방향의 품질 부족은 활성 방향 결과의 사용을 막지 않는다.

### 수급 상태 전달

`DailyCommentSignal`과 LLM 요청까지 `supply_data_status`와
`supply_observed_at`을 전달한다. Calibration 계산식은 estimated·confirmed에 따라
바뀌지 않지만, 화면·보고서 표시와 최신 상태 갱신 판정은 두 필드를 사용한다.

### 모델 배포 단위

다음 세 산출물을 하나의 활성 서비스 배포 묶음으로 취급한다.

```text
Positive model bundle
Negative model bundle
같은 모델 버전의 signal calibration JSON
```

세 산출물의 버전·토큰 계약·artifact ID 검증이 모두 끝난 뒤에만 활성 모델 버전을
전환한다. Calibration 파일은 Git 비추적 산출물이므로 배포 환경에 실제 파일이 있는지도
자동화 시작 전 확인한다.

같은 모델 버전 경로의 calibration은 운영에서 덮어쓰지 않는다. 현재 CLI의
`--overwrite`는 승인된 수동 복구·개발 검증 외에는 사용하지 않고, 모델이나 분포가
달라지면 새 모델 버전으로 생성한다.

### 대상 없음과 LLM client 생성

현재 보고서 실행기는 대상 조회 전에 LLM 환경설정과 client를 생성한다. 자동화에서는
보고서 대상이 0건이거나 모든 대상이 deterministic 결과인 경우 불필요한 외부 client를
먼저 만들지 않는다.

```text
calibration·모델 identity 검증
→ 보고서 대상과 신호 계산
→ 대상 0건이면 정상 종료
→ 실제 LLM 호출이 필요한 첫 대상에서 client 지연 생성
```

Calibration 누락과 identity 불일치는 대상 없음과 달리 활성 배포 오류이므로 정상
상태로 삼키지 않는다.

## 8. 일별 문서 스냅샷 개선 후보

현재 append-only 스냅샷 목적을 유지하면서 다음 개선을 검토할 수 있다.

### 생성 빈도 조절

- 자동화가 실행될 때마다 무조건 생성하지 않고 신규 토큰화 댓글이 있을 때만 생성한다.
- 현재 대상 조회도 미매핑 신규 댓글이 있는 종목·날짜만 선택하므로 이 기준은 구현돼 있다.
- 운영 데이터가 충분히 쌓인 뒤 10분 주기 유지, 더 긴 debounce 또는 장 마감 최종 생성
  중 어떤 방식이 서비스에 필요한지 실행시간·저장량으로 판단한다.

`debounce`는 짧은 시간에 변경이 여러 번 발생해도 일정 시간 동안 모아 한 번 처리하는
방식이다. 댓글 변화의 즉시성을 어느 정도 늦추는 대신 스냅샷 수를 줄일 수 있다.

### 동일 스냅샷 방지

- `document_hash`는 현재 생성·저장되지만 코드에서 기존 해시 조회나 중복 판정에
  사용되지 않는다. 현재 역할은 문서 내용과 구성 댓글의 고정 길이 지문이다.
- 향후 `document_hash`를 이용해 완전히 같은 댓글 구성의 문서가 중복 생성되는지
  확인하고, 동일 해시라면 새 스냅샷 적재를 생략할 수 있다.
- 실제 DB의 해시 고유키와 동시 실행 조건은 학원 환경에서 확인한다.
- 최상위 실행기의 중복 실행 방지는 스냅샷 중복과 DB 경합을 막는 기본 조건이다.

댓글이 추가되면 `tokenized_comment_id` 목록과 `tfidf_text`가 바뀌므로 새 해시가
생성된다. 따라서 동일 해시 중복 방지는 변경된 스냅샷 보존 목적과 충돌하지 않는다.

### LLM 입력 해시와의 구분

LLM 보고서의 `input_hash`는 현재 실제 재실행 판정에 사용된다.

```text
보고서 요청 DTO와 최종 system·user 메시지
→ input_hash 계산
→ 같은 생성 고유키의 기존 보고서 조회
→ 같은 hash면 LLM 호출과 INSERT 생략
→ 다른 hash면 허용된 수급 갱신인지 확인
```

DB UNIQUE 제약만 사용하면 LLM 호출이 끝난 뒤 INSERT에서 중복을 발견할 수 있다.
사전 해시 비교는 불필요한 요청 비용을 막고, 같은 결과 ID·provider·버전 조합 아래에서
근거 또는 최종 프롬프트가 조용히 바뀌는 것을 탐지한다. 현재 해시는 조회 속도 개선보다
멱등성과 입력 무결성 검증이 목적이다. 같은 문서의 더 최신 수급 관측이나 확정 전환만
제한적으로 보고서 UPDATE를 허용하고, 그 외 입력 변경은 계속 오류로 처리한다.

### 보존 정책

- MVP에서는 모든 스냅샷을 보존한다.
- 실제 운영 데이터가 커진 뒤에만 과거 장중 스냅샷의 보존 기간이나 간격 축소를 검토한다.
- 장 마감 최종 스냅샷과 발표·분석 근거로 사용된 스냅샷은 우선 보존한다.
- 삭제·축약 정책은 추론 결과와 LLM 보고서 참조 관계를 확인한 뒤 별도 결정한다.

현재 단계에서는 최신 행 UPSERT나 과거 스냅샷 삭제를 구현하지 않는다.

## 9. 리뷰·파일 의존 코드 정리 후보

다음 코드는 운영 DB 실행기와 다른 로컬 검수·발표 분석 경로에서 사용된다.

- `analysis/daily_dataset.py`의 `iter_daily_documents()`
- `analysis/daily_dataset.py`의 `create_labeled_daily_dataset()`
- `analysis/review.py`의 파일 기반 검수 흐름
- 과거 JSONL·파일 입력을 전제로 남은 함수

발표자료의 재현 근거로 사용할 가능성이 있으므로 현재 삭제하지 않는다. 발표자료에서
사용할 함수와 산출물을 확정한 뒤 호출자를 다시 조사해 다음으로 구분한다.

```text
운영 경로
발표·검수 경로
확실한 미사용 레거시
```

챗봇 병합 이후 구조 개편 브랜치에서 검수 코드를 별도 위치로 이동하고, 호출자가 없는
레거시만 삭제한다.

`analysis/notebooks/`는 현재 구현에 도달하기 위한 실험·테스트·검증 기록이다. 일부
Notebook이 과거 함수명을 참조하더라도 운영 기능의 오류로 판단하지 않는다. 발표에서
TF-IDF 설정 선택, Ridge 실험과 구현 전환의 근거로 사용할 가능성이 있으므로 발표
전에는 삭제하지 않고 운영 코드 복기 대상에서 제외한다. 발표 이후 사용 여부에 따라
보존, `archive` 이동 또는 미사용 파일 삭제를 결정한다.

## 11. 완료 확인

1. 단일 댓글과 배치 토큰화가 같은 설정을 사용한다.
2. 동일한 입력에서 두 경로의 선택 토큰이 일치한다.
3. 현재 `kiwi_ver1` 설정은 수정하지 않는다.
4. DB 컬럼명 불일치는 실제 스키마 확인 전까지 보류 상태로 보고한다.
5. 최상위 실행기는 토큰화 실패 후 일별 문서 단계로 넘어가지 않는다.
6. 수행한 검증과 현재 환경에서 확인하지 못한 항목을 구분해 기록한다.
7. 일별 문서 실패가 있으면 후속 추론을 시작하지 않는다.
8. 일별 문서는 UPSERT하지 않고 댓글 구성 변화의 스냅샷으로 보존한다.
9. 학습·추론·단일 댓글·LLM의 공통 서비스 모델 설정을 중립 모듈 한 곳에서 관리한다.
10. 추론 전에 현재 토큰 버전과 DB 아티팩트·모델 bundle의 토큰 버전이 일치한다.
11. calibration과 LLM 보고서가 현재 활성 모델 식별값과 일치하지 않으면 중단한다.
12. 일별 문서 해시와 LLM 입력 해시의 현재 사용 여부를 구분해 설명한다.
13. 활성 모델을 검증한 뒤 DB 현재 상태 기준으로 미완료 추론 대상을 조회한다.
14. 추론 대상이 없으면 성공 0건·실패 0건으로 정상 종료한다.
15. 방향별 추론 품질 상태와 feature 수·coverage를 DB에 저장하고 서비스가 재사용한다.
16. `estimated`는 추정 상태로, `confirmed`는 확정 상태로 화면과 보고서에 표시한다.
17. 확정 전환 시 모델을 재추론하지 않고 활성 방향과 LLM 보고서를 갱신한다.
18. 같은 문서의 confirmed 보고서를 estimated 입력으로 되돌리지 않는다.
19. Positive·Negative bundle과 calibration 전체 identity를 운영 시작 전에 검증한다.
20. Calibration 생성은 새 모델 준비 절차에만 포함하고 10분 자동화에서는 재생성하지 않는다.
21. 활성 추론 결과의 DB `inference_status`를 신호 계산의 단일 품질 기준으로 사용한다.
22. 보고서 대상이 없으면 외부 LLM client를 생성하지 않고 정상 종료한다.
23. LLM 일부 대상 실패가 정상·기존 보고서의 Chroma 색인을 막지 않는다.
24. 최상위 실행기는 Chroma 실행함수의 대상·신규·갱신·기존·제외·실패 수를 기록한다.
